= Solution Design

== On-Chain Wallet Support & Transfer (Issues #10, #11)

=== Overview

Adds on-chain Bitcoin wallet support (watch-only via xpub) alongside existing NWC Lightning wallets, plus a Transfer feature for moving funds between wallets and Boltz submarine swaps for Lightning-to-on-chain payments.

**Why BDK?**

Previously, on-chain wallet operations used manual Electrum JSON-RPC calls (`electrum-client` + `react-native-tcp-socket`) with `bitcoinjs-lib` for transaction parsing. This approach had multiple issues:

- Fragile TCP/SSL connections that dropped under load
- Manual raw transaction parsing to determine amounts (slow, unreliable)
- Couldn't determine outgoing tx amounts without looking up each input's previous output
- No timestamps without fetching block headers
- Rate limiting / connection drops with many sequential requests

BDK (same library used by https://peachbitcoin.com[Peach Bitcoin]) handles all of this natively in Rust via a single `wallet.sync()` call, providing correct balance, transaction history with amounts/directions/timestamps, and address derivation.

**Metro configuration:** `@noble/curves` and `@noble/hashes` use ES module `exports` maps with `.js` extensions. A custom resolver in `metro.config.js` rewrites `@noble/*` subpath imports to include `.js` extensions, using the original resolver to avoid recursion.

=== Boltz Reverse Submarine Swap (Lightning → On-chain)

Uses https://docs.boltz.exchange[Boltz Exchange] v2 API for trustless cross-chain transfers. Verified against https://api.docs.boltz.exchange/lifecycle.html[Boltz v2 lifecycle docs] and reference implementations (boltz-core, Breez SDK).

==== Reverse Swap: Lightning → On-chain (`claimSwap`)

1. Generate random 32-byte preimage + SHA-256 hash
2. Generate temporary secp256k1 claim keypair
3. `POST /v2/swap/reverse` with `preimageHash`, `claimPublicKey`, `claimAddress`, `referralId` and either:
   - `onchainAmount` = recipient amount + claim-fee budget — the Send sheet (#1175). The recipient gets exactly what was asked; Boltz's fee, its lockup fee and our claim fee all land on the invoice (`utils/reverseSwapAmounts.ts` mirrors Boltz's `calculateReverseSwapAmounts` so the invoice amount can be verified exactly). Boltz echoes no `onchainAmount` in this mode; the lockup is verified against ours. The claim pays the recipient exactly when the budget still covers the live claim fee, otherwise the live fee comes out of the lockup.
   - `invoiceAmount` — Move to an own on-chain wallet; fees come off the on-chain side.
4. Boltz returns a Lightning invoice + swap tree (Taproot HTLC scripts)
5. **Persist** the full swap state to SecureStore (preimage, claimPrivateKey, lockupAddress, destinationAddress, refundPublicKey, swapTree) AND register the swap ID in `swapRecoveryService` — see "Persistence + Recovery contract" below
6. Pay the Lightning invoice via NWC
7. Subscribe to swap status via WebSocket (`wss://api.boltz.exchange/v2/ws`) with polling fallback
8. Wait for `transaction.mempool` or `transaction.confirmed`
9. Construct **script-path claim transaction** (Taproot spend):
   - Witness: `<schnorr_sig_64bytes> <preimage> <claim_script> <control_block>`
   - Uses SIGHASH_DEFAULT (0x00) — 64-byte signature, no sighash byte appended
   - Script lengths encoded with Bitcoin CompactSize varint
   - Internal key: **MuSig2 key-aggregation** (BIP-327) of Boltz's `refundPublicKey` and our `claimPublicKey` — see "Taproot internal key derivation" below
10. Broadcast claim tx via BDK Electrum
11. Clean up persisted swap state on success

==== Submarine Swap: On-chain → Lightning (`refundSwap`)

1. Generate LN invoice on destination NWC wallet
2. Generate temporary secp256k1 refund keypair
3. `POST /v2/swap/submarine` with `invoice`, `refundPublicKey`, `referralId`
4. Boltz returns on-chain address + expected amount + swap tree + claimPublicKey
5. Persist swap state (refundPrivateKey, claimPublicKey, swapTree, timeoutBlockHeight) to SecureStore
6. Send BTC from hot wallet to Boltz address via BDK
7. Subscribe to swap status via WebSocket with polling fallback
8. Wait for `invoice.settled` or `transaction.claimed`
9. Clean up persisted swap state on success

**Refund recovery** — if swap fails (`swap.expired`, `invoice.failedToPay`, `transaction.lockupFailed`):

1. Fetch lockup UTXO details via `GET /v2/swap/submarine/{id}/transaction`
2. Construct **script-path refund transaction**:
   - `nLockTime` = `timeoutBlockHeight` (refund only valid after timeout)
   - Input sequence `0xFFFFFFFE` (enables nLockTime)
   - Witness: `<schnorr_sig_64bytes> <refund_script> <control_block>` (no preimage needed)
   - Internal key: Boltz's `claimPublicKey`
   - Merkle sibling: `claimLeafHash`
3. Broadcast refund tx via BDK Electrum

==== Persistence + Recovery contract

The reverse and submarine flows generate **random** secrets in JS memory (preimage, claim privkey for reverse; refund privkey for submarine). If the app dies or `claimSwap` / `refundSwap` throws before the on-chain side is finalised, those secrets are lost and the funds in the HTLC become unspendable for the user.

The contract that prevents that loss has three parts:

. **Write-before-pay.** *Before* the Lightning invoice is paid (reverse) or the on-chain HTLC is broadcast (submarine), the caller writes:
+
[source,ts]
----
await SecureStore.setItemAsync(`boltz_swap_${swap.id}`, JSON.stringify({
  id, preimage, claimPrivateKey, lockupAddress,
  destinationAddress, refundPublicKey, swapTree,
}));
await swapRecoveryService.registerPendingSwap(swap.id);
----

. **Delete-on-success.** When the swap fully settles, the same caller deletes the SecureStore record and unregisters from the index:
+
[source,ts]
----
await SecureStore.deleteItemAsync(`boltz_swap_${swap.id}`);
await swapRecoveryService.unregisterPendingSwap(swap.id);
----

. **Leave-on-failure.** Any throw between (1) and (2) is *re-thrown without cleanup*. The persisted record is the safety net — `swapRecoveryService.recoverPendingSwaps` re-reads it on next launch.

**Caller surface.** Both code paths now follow this contract:

* `src/components/TransferSheet.tsx` — Home → Transfer (LN→on-chain *and* on-chain→LN). Has done so since the original Boltz integration.
* `src/components/SendSheet.tsx` — Home → Send → paste BIP-21. Brought up to contract by the #481 fix (was previously memory-only and lost secrets on every claim failure).

**Recovery service.** `src/services/swapRecoveryService.ts` runs on every `WalletContext` mount (`src/contexts/WalletContext.tsx:426`). For each swap ID in the index it:

. Reads the per-swap blob from SecureStore.
. Calls Boltz `GET /v2/swap/{id}` to find current status.
. If `transaction.mempool` or `transaction.confirmed`: builds and broadcasts a fresh claim tx using the persisted secrets, then deletes the record on success.
. If the swap is already settled or failed: cleans up the record.
. If the API rejects the swap as expired beyond recovery: surfaces a "Swap recovery failed" toast and clears the record so it doesn't retry forever.

**User-facing affordances.**

* `TransferSheet` shows a "Recovery retried" overlay after a background failure, with a **Retry now** button that re-runs the same recovery routine immediately rather than waiting for the next launch.
* `SendSheet` (after the #481 fix) re-throws errors with a `"Boltz swap failed: <detail>"` prefix so the failure overlay shows the underlying claim error instead of "unknown Error". The persisted record means a force-stop + relaunch will quietly settle the on-chain side.

**Observed during the #481 fix work (2026-05-10):** the first claim attempt on a freshly created reverse swap was failing *deterministically* with an opaque `"unknown Error"`. Root cause: the Alby SDK wraps NIP-47 responses with empty error bodies as `Nip47WalletError("unknown Error", "INTERNAL")` *even when the wallet processed the payment* — `nwcService.payInvoice` now looks up the invoice in that case (mirroring the existing "failed to publish" handler) and returns the preimage if found, so fresh swaps no longer trip the recovery path at all. The persistence + retry layer remains as defence in depth for genuine claim failures. Two real-money 30k swaps via SendSheet and TransferSheet on Big Piggy validated the end-to-end recovery path before the root-cause fix landed.

==== Taproot Internal Key Derivation (MuSig2)

Boltz v2 swaps use a Taproot output whose internal key is a **MuSig2 key-aggregation** (BIP-327) of two keys: Boltz's pubkey and ours. The exact order matters — Boltz's docs state **"Boltz's public key always coming first"**:

[cols="1,1,1", options="header"]
|===
| Swap type | Boltz's role | `keyAggregate` order

| Reverse swap (LN → on-chain) | Refunder | `[refundPublicKey, claimPublicKey]` (our claim key is ours)
| Submarine swap (on-chain → LN) | Claimer | `[claimPublicKey, refundPublicKey]` (our refund key is ours)
|===

Keys must be **33-byte compressed** (not x-only) for `keyAggregate`. The aggregate is then used as the internal key when computing `TapTweak(aggPubkey ‖ merkleRoot)` and building the control block. Merkle root is `TapBranch(sorted(claimLeafHash, refundLeafHash))` per BIP-341.

We use `@scure/btc-signer`'s `keyAggregate` + `keyAggExport` from `musig2.js` (MIT-licensed). Boltz's own `boltz-core` uses the same library internally but is AGPL-3.0, so we depend on `@scure/btc-signer` directly.

Diagnostic cross-check: computing `p2tr(internalKey, [claimLeaf, refundLeaf], undefined, /*allowUnknownOutputs*/ true)` from `@scure/btc-signer` and comparing `.script` to the on-chain lockup scriptPubKey confirms the derivation is correct. See `TROUBLESHOOTING.adoc` for the witness-hash-mismatch symptom and debugging procedure.

References:

* https://api.docs.boltz.exchange/claiming-swaps.html[Boltz — Claims & Refunds]
* https://bips.dev/327/[BIP-327 — MuSig2]
* https://bips.dev/341/[BIP-341 — Taproot]

==== Status Monitoring

Swap status is monitored via **WebSocket subscription** to `wss://api.boltz.exchange/v2/ws`:

```json
{"op": "subscribe", "channel": "swap.update", "args": ["<swapId>"]}
```

Falls back to HTTP polling (`GET /v2/swap/{id}` every 3s) if WebSocket fails. All production Boltz clients (Breez SDK, boltz-client) use WebSocket.

==== Swap Recovery (`swapRecoveryService`)

Reverse swaps involve three critical steps that must complete for funds to be recovered:

1. Pay the Lightning invoice (via NWC `pay_invoice`)
2. Wait for Boltz to lock funds on-chain (`waitForLockup`)
3. Build & broadcast the claim transaction (`claimSwap`)

If the app crashes, loses connection, or the `pay_invoice` NWC call times out (e.g. because the payment took longer than the ~60s NWC SDK timeout), the swap can be stranded — Boltz has received the LN payment and locked on-chain funds, but the user never claims them. After the CSV timeout, Boltz auto-refunds their locked funds, and the user loses the Lightning payment.

**Recovery mechanism:**

- When a reverse swap is created, full state is persisted to SecureStore under `boltz_swap_<id>`: `preimage`, `claimPrivateKey`, `lockupAddress`, `destinationAddress`, `refundPublicKey`, and `swapTree`.
- A separate index key `boltz_swap_index` tracks active swap IDs (SecureStore has no listing API).
- On app startup, `recoverPendingSwaps()` runs in the background:
  1. Read the index, iterate over each swap ID.
  2. Query `GET /v2/swap/{id}` for current status.
  3. If `transaction.mempool` or `transaction.confirmed`, call `claimSwap` to broadcast the claim tx.
  4. If terminal success/failure, clean up the persisted state and remove from index.
- After successful claim (or on original swap completion), `unregisterPendingSwap()` removes the swap from tracking.

This makes reverse swaps **crash-safe** — if anything interrupts the foreground swap flow (app kill, network drop, NWC timeout), the claim is retried on next app launch.

**Note**: older persisted swaps (created before v1 of the recovery service) lack `swapTree` and `refundPublicKey`. These cannot be auto-recovered and their funds will be refunded to Boltz after the CSV timeout.

==== Script-Path vs Cooperative Key-Path

Boltz v2 Taproot swaps support two spending methods:

- **Key-path (cooperative MuSig2):** Requires nonce exchange between client and Boltz. Smaller on-chain footprint (~30-50% fee savings), better privacy. Requires MuSig2 library.
- **Script-path (non-cooperative):** Standard Schnorr signature + preimage/timelock. Works with pure JS crypto. Slightly larger witness but settles identically.

We use **script-path** for both claims and refunds because MuSig2 is not available in our JS stack. This matches boltz-python and Breez Go client. Future: upgrade to cooperative key-path when MuSig2 support is available.

=== Electrum Server Integration

On-chain balance and transaction lookups use the Electrum protocol via BDK's native Rust implementation. BDK handles the Electrum connection, address scanning, UTXO tracking, and transaction parsing internally — `onchainService.ts` just calls `wallet.sync(blockchain)`.

- **User-configurable** — default is `electrum.blockstream.info:50002` (SSL), users can set their own in Account settings (host:port + SSL toggle)
- **Incremental sync (current session only)** — BDK fetches changes since the last sync within the current JS session. We use `DatabaseConfig().memory()` so sync progress does not persist across app restarts; the first sync after launch is a full chain scan. Switching to a persistent database config is a future improvement.
- **Native performance** — Electrum communication runs in Rust, not in JS TCP sockets
- **Correct amounts** — BDK tracks `received` and `sent` per transaction using UTXO analysis

**Electrum server format:** `host:port:protocol` where protocol is `s` (SSL) or `t` (TCP). Account settings shows host:port with a "Use SSL" toggle.

**Transaction caching:** Transactions are stored per wallet in `WalletContext` and persisted to AsyncStorage. On startup, cached transactions display immediately (~40ms); BDK syncs fresh data in the background.

=== NWC Relay Compatibility

The LNbits Nostrclient relay proxy does not send NIP-01 OK responses after receiving EVENT messages (see https://github.com/lnbits/nostrclient/issues/52[lnbits/nostrclient#52]). This causes `nostr-tools` `SimplePool.publish()` to timeout, breaking all NWC operations.

**Workaround in `nwcService.ts`:** The relay pool's `publish` method is monkey-patched during `connect()` to resolve immediately (fire-and-forget) instead of waiting for OK. The NWC response comes back via the subscription, not the OK acknowledgement.

**Proper fix:** PR https://github.com/lnbits/nostrclient/pull/68[lnbits/nostrclient#68] adds NIP-01 OK and CLOSED responses to Nostrclient. Once merged, the monkey-patch can be removed.

Additionally, `nwcService.ts` includes auto-reconnect logic: if a publish fails with "failed to publish" (relay disconnected), it creates a fresh `NostrWebLNProvider` and retries. The wallet is marked as "Connected" after `enable()` succeeds, not after `getBalance()`, so slow relay responses don't show the wallet as disconnected.

=== NWC Connection Reliability

Multiple layers protect against NWC relay disconnections:

1. **Proactive check**: `ensureConnected()` checks `client.connected` before every NWC operation — reconnects immediately if the WebSocket dropped
2. **Connection polling**: Every 30 seconds, poll `isWalletConnected()` and update the wallet card status dot
3. **Publish patch**: Monkey-patch the relay pool to not wait for NIP-20 OK responses (lnbits/nostrclient#52 workaround, can be removed once lnbits/nostrclient#68 is merged)

=== Honest Payment-State UX

Lightning HTLCs that traverse hold-invoice routers (e.g. Boltz Mini for LN→RBTC bridges that Geyser's Rootstock crowdfunding uses) can stay locked for 60–120 seconds while the off-chain leg confirms. RSK target block time is ~24 s with exponential inter-arrival times; ~5 % of blocks land beyond 72 s, ~1 % beyond 110 s. The recipient sees the payment settle at preimage reveal. The sender's *progress overlay* is driven by the synchronous NIP-47 reply event: until that event lands (or the local timeout fires) the overlay can't move from "Sending" to a definitive success/failure state. The transaction *list*, by contrast, can update later via the regular `fetchTransactionsForWallet` polling/reconciliation path — so even if the user dismisses the overlay before the reply arrives, the row eventually flips from optimistic to confirmed/failed once LNbits exposes the settlement.

If the app applies a hard local timeout shorter than the worst-case settle, two failure modes follow:

1. **False "failed" message** — the user sees an error, but the HTLC is still in flight. Risk of double-pay; user panics; recipient eventually gets paid and sender wonders where the sats went.
2. **Misleading "Cancel" affordance** — once an HTLC is on a route, the sender genuinely cannot cancel it. The action only stops *waiting*; the lock keeps ticking.

The honest design (see #410, #428):

* **Reply timeout = 90 s.** With RSK's ~24 s mean exponential inter-arrival, this catches `1 - e^(-90/24)` ≈ 97.6 % of bridge-bound payments. Beyond that, switch to "still in flight" state rather than "failed". (Initial bump in #427.)
* **Modal action = "Continue in background"**, styled as a real button with proper hit affordance. NOT "Cancel".
* **In-flight UI copy**: "Lightning payments via bridge nodes can take 1–2 min. The result will appear in your transactions once the network settles."
* **Optimistic-row reconciliation**: dismissing the overlay does NOT remove the optimistic transaction row from `wallets[].transactions`. The next `fetchTransactionsForWallet` (already triggered on tab focus + pull-to-refresh) reconciles by `paymentHash` — if the LNbits ledger now shows the payment as settled, the row updates from optimistic to confirmed; if it shows failed, the row goes red (#426).
* **Reply-event listening (deferred)**: the longer-term shape is to drop the local timer entirely and react to the eventual NIP-47 reply event whenever it arrives — no matter how late. Deferred to a follow-up under #410 because it requires extending the Alby SDK wrapper to keep a long-lived listener post-`payInvoice`.

Distinguishes three reply outcomes:

[cols="1,2", options="header"]
|===
| Reply state | UX
| NWC error response (`payment_error`) within 90 s | Red toast + bubble red (#426) — payment definitively failed
| Reply timeout (90 s, no response) | "Still in flight" + "Continue in background" — let the network settle
| NWC reply success | Green tick + bubble green
|===

=== Hot Wallet Support (Secret Mode)

Hot wallet (mnemonic import) is available behind a **secret mode** toggle:

- **Enable**: Triple-tap the version number at the bottom of Account settings
- **Stored**: `secret_mode_<pubkey>` flag in AsyncStorage (per account, persists across sessions)
- **Visual**: Version displays "(secret)" suffix when enabled

**Mnemonic import flow:**

1. User selects "Import Seed Phrase (Beta)" in Add Wallet wizard (secret mode only)
2. Enters 12 or 24 word mnemonic — input normalised: strips numbers, colons, extra whitespace, lowercased
3. Mnemonic validated via `bip39.validateMnemonic()`
4. Stored in `expo-secure-store` (encrypted device storage) under `onchain_mnemonic_{walletId}`
5. BDK creates a full signing wallet via `Descriptor.newBip84()` with `DescriptorSecretKey`

**Sending from hot wallets:**

- Send button enabled for hot wallets (disabled for watch-only xpub imports)
- `onchainService.sendTransaction()` uses BDK's `TxBuilder` for UTXO selection + fee calculation, `wallet.sign()` for signing, and `blockchain.broadcast()` for broadcasting
- All signing happens locally on-device — private keys never leave the device

**Watch-only vs hot wallet detection:**

- `onchainImportMethod` field in `WalletMetadata`: `'xpub'` (watch-only) or `'mnemonic'` (hot)
- `onchainService.isWatchOnly()` checks if a mnemonic is stored for the wallet
- HomeScreen Send button uses this to enable/disable

=== Transaction Caching

Transactions are owned by `WalletContext` (not local HomeScreen state):

- Each `WalletState` has a `transactions: WalletTransaction[]` array
- On startup, cached transactions loaded from AsyncStorage (`txs_{walletId}`) — renders in ~40ms
- On wallet swipe, the right list shows in the same frame as the card (#1304). `WarmTransactionLists` keeps one memoised `TransactionList` mounted per *warm* wallet (the active card and its neighbours, at most three), so a swipe only changes which list is visible instead of re-rendering one list with new rows
- `walletRefreshScheduler` (pure) refreshes the active card ~300 ms after it settles, then warms its NWC neighbours one at a time, skipping anything loaded in the last 30 s. On-chain cards refresh at most every 5 min (a BDK sync holds the JS thread) and aren't prefetched
- Background refresh via `fetchTransactionsForWallet()` (in `useWalletTransactionsFetch`) syncs with BDK/NWC. It resolves whether it succeeded, so a failed fetch is retried on the next activation instead of counting as fresh; fetches are serialised per wallet
- `TransactionList` renders first 20 transactions with "Show all N transactions" button to avoid render blocking (was causing 4+ second delay with 259 txs)

== Authentication

Two sign-in methods are supported:

=== nsec (Private Key)

1. User enters `nsec1...` key in the login sheet
2. Key is decoded via `nostr-tools/nip19` to derive the pubkey
3. nsec stored in `expo-secure-store` (encrypted device storage)
4. All event signing done locally with `nostr-tools/pure.finalizeEvent()`

=== Amber Signer (Android only)

1. App sends an intent to the Amber app via `Linking.openURL()`
2. Amber returns the pubkey (no private key ever leaves Amber)
3. Pubkey stored in `expo-secure-store`
4. Event signing delegated to Amber via NIP-55 intents

=== Auto-Login on Startup

On app launch, `NostrContext` checks `expo-secure-store` for stored credentials:

- **nsec path**: reads stored nsec, derives pubkey, sets `isLoggedIn = true`
- **Amber path**: reads stored pubkey, sets `isLoggedIn = true`

No re-authentication with Amber is needed on startup. The pubkey alone is sufficient to restore the logged-in state and fetch all public data.

=== Account Creation

New users can generate a Nostr identity directly in the app:

1. `nostr-tools/pure.generateSecretKey()` creates a new keypair
2. User enters a display name
3. nsec is stored and the user is logged in
4. A kind 0 (metadata) event is published with the display name
5. User is shown their nsec with a copy button and backup warning

=== Relay health

`src/services/relayHealth.ts` remembers relays that fail to connect, and both relay pools (the shared one in `src/services/nostrPool.ts` and the market snapshot's, via the `withRelayHealth` mixin in `src/services/healthAwarePool.ts`) skip them:

* Two corroborated connect failures or timeouts park a relay for 15 min, doubling per further failure up to 6 h. A success clears it. A failure only counts if another relay connected within 30 s, so an offline phone doesn't park everything.
* Subscriptions and publishes leave parked relays out, but always keep the healthiest 2 relays of a request.
* Every connection attempt is capped at 5 s. Before, nostr-tools used 80 % of the query's `maxWait`, so a 15 s query waited 12 s for a relay that never answered.
* State is in memory, with a debounced AsyncStorage copy, so known-dead relays are skipped from the first query after a cold start.
* Users' own kind-10002 lists are never rewritten. A dead relay in them is just skipped while it's parked.

=== NIP-65 User Relays

On login, the app fetches the user's kind 10002 event to discover their preferred read/write relays. These are merged with the defaults for all subsequent operations.

== Performance

Loading 500+ contacts with profiles requires careful optimization:

=== Caching

- Contact list and profiles cached in `AsyncStorage` with 24-hour TTL
- On startup, cached contacts load in ~40ms (no network)
- Fresh data fetched in background via `InteractionManager.runAfterInteractions`

=== Rendering

- `@shopify/flash-list` replaces FlatList for cell recycling (5-10x faster)
- `React.startTransition()` wraps all `setContacts` calls for non-blocking renders
- `freezeOnBlur: true` on tab navigator prevents re-renders on hidden tabs
- Context value memoized with `useMemo` to prevent unnecessary consumer re-renders

=== Profile Fetching

- Batches of 50 pubkeys, 3 concurrent batches, 12s timeout per batch
- 50ms yield between batch rounds for UI responsiveness
- `onBatch` callback updates UI incrementally as profiles arrive
- `expo-image` with `cachePolicy="memory-disk"` for profile pictures (see "Avatar caching convention" below)

=== Avatar caching convention

Every avatar render site (any `<Image>` / `<ExpoImage>` rendering a contact / account / team profile picture) must use `expo-image` with `cachePolicy="memory-disk"`, `recyclingKey={uri}`, and `autoplay={false}`. `memory-disk` keeps the decoded bitmap in memory across renders (no re-fetch on scroll); `recyclingKey` lets FlashList / FlatList reuse the decoded bitmap when a row recycles (no flash of the previous row's avatar); `autoplay={false}` shows the first frame only for animated WebP / GIF avatars (no per-row FrameDecoderExe thread). Audited and standardised across the codebase in issue #477. Banners, splash artwork, course / mission thumbnails, wallet card art, and link-preview thumbnails are deliberately out of scope — they have their own caching needs (or none).

== Image Upload

Used by three flows: profile picture / banner (EditProfileSheet), chat image attachments (ConversationScreen). All three funnel through the same helper chain in `src/services/imageUploadService.ts`.

=== Pipeline (ordered)

1. **Pick & crop** — `expo-image-picker` with `allowsEditing: true`, `quality: 1`, 1:1 aspect for avatars, 3:1 for banners.
2. **Strip EXIF metadata** — `stripImageMetadata()` re-encodes the image through `expo-image-manipulator` at `compress: 0.9`, `format: JPEG`, `base64: true`. Re-encoding drops every EXIF chunk (GPS coordinates, capture timestamp, camera Make/Model, Software, …) — no tag-by-tag allowlist needed; the fresh JPEG has no metadata segments at all. Quality is `1` at the picker (not `0.8`) so the manipulator's `0.9` is the only lossy step. Returns `{ uri, base64 }`. Privacy rationale: issue #145.
3. **Upload** — `uploadImage(uri, signer, base64)`:
** **Signed in (nsec or Amber)** → `uploadToBlossom(uri, server, signer, base64)`. Blossom PUT with a BUD-02 signed auth event (`kind: 24242`). Server is user-configurable (`getBlossomServer()`), defaults to the Lightning Piggy–hosted instance. See BUD-01 / BUD-02 at https://github.com/hzrd149/blossom.
** **Not signed in (public key only / hot wallet)** → `uploadToNostrBuild(uri)`. Anonymous `POST https://nostr.build/api/v2/upload/files` with multipart/form-data. Fallback only; no kind-0 publish path hits this branch because profile edits require signing.

=== Why base64 is forwarded inline

`uploadToBlossom` requires the image bytes. Reading `file://` URIs via `fetch` / `XHR` is flaky on Android React Native (encoding lossage, race with `AsyncStorage` locking). The picker's `base64: true` / manipulator's `base64: true` outputs bypass that by passing the bytes in memory as a base64 string; `blossomService.ts` then `Buffer.from(base64, 'base64')` to get the raw `Uint8Array` for the PUT body. Issue #141 regressed because a prior refactor dropped this forwarding.

=== Key files

- `src/services/imageUploadService.ts` — `stripImageMetadata`, `uploadImage`, `uploadToNostrBuild`.
- `src/services/blossomService.ts` — Blossom BUD-02 signing (`kind: 24242`, 5-min expiration), XHR binary PUT, response parsing. Logs `[Blossom] uploaded <url>` on success — grepped by `scripts/verify_exif_strip.sh`.
- `src/components/EditProfileSheet.tsx` `pickAndUpload` — profile flow.
- `src/screens/ConversationScreen.tsx` `uploadAndSendImage` — chat flow.

=== Verification

- `.maestro/profile/flow-096-edit-profile-picture.yaml` — drives the UI, asserts no `Upload Failed` alert (#141 regression guard).
- `.maestro/messaging/flow-067-exif-strip.yaml` + `scripts/verify_exif_strip.sh` — two-stage check: Maestro drives upload, shell wrapper seeds a JPEG with known GPS / Make / Model / DateTimeOriginal / Software tags, greps logcat for the Blossom URL, downloads the uploaded bytes, and asserts `exiftool` sees none of the seeded tags. Exits 3 on privacy regression.

== Direct Messages (NIP-04 + NIP-17)

The Messages tab is a conversations inbox backed by two Nostr DM specs running side-by-side.

=== Protocols

- **https://github.com/nostr-protocol/nips/blob/master/04.md[NIP-04] — legacy.**
  Single kind-4 event with AES-256-CBC content. Sender pubkey, recipient `p` tag, and `created_at` are all plaintext on the wire — the spec notes this leaks metadata. Deprecated by the spec text itself in favour of NIP-17.
- **https://github.com/nostr-protocol/nips/blob/master/17.md[NIP-17] — the modern form.**
  Three layers: kind-14 *rumor* (unsigned plaintext message) → kind-13 *seal* (NIP-44-encrypted, signed by the real sender) → kind-1059 *gift wrap* (NIP-44-encrypted to the recipient, signed by a disposable ephemeral key). Only the outermost wrap hits relays. Visible fields on the wrap: random `pubkey`, randomized `created_at` (up to 2 days in the past), `kind: 1059`, and a `p` tag for the recipient. Sender identity, message kind, tags, and true send time are all hidden inside the payload.
- **https://github.com/nostr-protocol/nips/blob/master/44.md[NIP-44] — the cipher.**
  secp256k1 ECDH + HKDF + ChaCha20 + HMAC-SHA256. The encryption primitive that NIP-17 uses at both layers. Not a DM spec on its own; appears in this codebase only as the tool NIP-17 calls for sealing.

The app accepts both inbound formats and currently sends only NIP-04. Migrating outbound to NIP-17 is tracked under the send-side NIP-17 issue; the inbox work here is explicitly the read-side.

=== Data flow (inbox list)

[source]
----
refreshDmInbox(NostrContext)
  │
  ├─ fetchInboxDmEvents(myPubkey, relays)
  │    three parallel pool.querySync calls:
  │      {kinds:[4],    authors:[me], limit:500}
  │      {kinds:[4],    #p:[me],      limit:500}
  │      {kinds:[1059], #p:[me],      limit:500}
  │
  ├─ per kind-4 event:
  │    1. derive partner = fromMe ? p-tag : ev.pubkey
  │    2. if partner not in followPubkeys → skip (no decrypt)        ←── follow filter
  │    3. decryptNip04ViaSigner(partner, ev.content)  (nsec or Amber)
  │    4. push DmInboxEntry
  │
  ├─ per kind-1059 event (Amber path):
  │    0. if NIP-17 toggle off → skip whole block
  │    1. cache.get(wrap.id) → if present and partner still followed, push
  │    2. unwrapWrapViaNip44(wrap, amberNip44DecryptSilent)
  │       - verifyEvent(wrap) sig check
  │       - layer 1: Amber silent nip44_decrypt → seal JSON
  │       - parseSeal runtime validator (kind === 13, fields typed)
  │       - layer 2: Amber silent nip44_decrypt → rumor JSON
  │       - parseRumor runtime validator
  │       - require rumor.pubkey === seal.pubkey (NIP-17 spec)
  │    3. partnerFromRumor(rumor, myPubkey)
  │    4. if partner not in followPubkeys → drop (no cache write)     ←── follow filter
  │    5. cache.set(wrap.id, entry); push DmInboxEntry
  │    6. on PERMISSION_NOT_GRANTED: set amberNip44Permission='denied'
  │       and stop iterating (no dialog flood)
  │
  ├─ per kind-1059 event (nsec path):
  │    same shape but via unwrapWrapNsec → nip59.unwrapEvent
  │
  └─ setDmInbox(entries) — identity-change guard first
----

The `followPubkeys` gate is a data-layer invariant: plaintext for non-followed senders never enters `dmInbox` React state or the persistent `amber_nip17_cache_v1` AsyncStorage map. `buildDmSummaries` re-applies the same filter when materialising summaries so that unfollowing a contact removes their rows on the next render even before the cache is next re-fetched.

=== Amber silent-path for NIP-17

Amber's `com.greenart7c3.nostrsigner` provider exposes two ways to call `nip44_decrypt`:

1. **ContentResolver fast-path** (silent) — used by our `nip44DecryptSilent` binding. Resolves only if the user has granted blanket permission for the op; rejects with `PERMISSION_NOT_GRANTED` otherwise.
2. **Intent fallback** (dialog) — used by the normal `requestNip44Decrypt` binding. Shows an approval dialog on every call unless the user previously ticked "Remember my choice".

The inbox refresh uses (1) exclusively so we never fan out one dialog per gift wrap when the user toggles NIP-17 support on for the first time. A failed silent call is caught, the denial is surfaced as `amberNip44Permission === 'denied'`, and Account shows a single grant-permission button that fires a one-off encrypt+decrypt probe round-trip through (2) — one dialog, user taps "Remember my choice", subsequent refreshes are silent.

`ConversationScreen`'s per-thread `fetchConversation` falls back to the Intent path for uncached wraps because that screen is user-initiated and the volume is small.

=== Persistent wrap-id cache

`amber_nip17_cache_v1` in AsyncStorage maps `wrap.id` → decrypted `DmInboxEntry`. Only rumors from followed senders ever land here. Capped at 5000 entries, trimmed by newest `createdAt`. Cleared on logout along with the `amber_nip17_enabled` toggle flag.

A single-flight guard (`useRef<Promise>`) coalesces overlapping `refreshDmInbox` calls so the `useFocusEffect` firing on tab focus doesn't race a pull-to-refresh on the same cache.

=== Shared helpers

- `src/utils/nip17Unwrap.ts` owns the two-layer decrypt pipeline used by both `refreshDmInbox` and `fetchConversation`. Runtime type-guards (`parseSeal`, `parseRumor`) reject malformed payloads; `verifyWrapSig` runs `verifyEvent` before trusting the wrap's `pubkey` / `content`. `unwrapWrapViaNip44(wrap, decryptNip44Callback)` works for any signer; `unwrapWrapNsec(wrap, secretKey)` is the nsec-specialised fast path.
- `partnerFromRumor(rumor, viewerPubkey)` centralises the "fromMe vs incoming" determination.
- `getMemoisedSecretKey(pubkey)` in `NostrContext` reads + bech32-decodes the nsec from SecureStore once per session; cleared on logout.

=== Following-only filter

"Following only" is treated as a safety boundary for the family-oriented UX: DMs from strangers are hidden from the inbox, the cache, and the thread view. The filter is enforced in three places:

1. `refreshDmInbox` — gates decrypt attempts (NIP-04) or cache writes + state commits (NIP-17).
2. `buildDmSummaries` — re-applies when summaries are built from state, so unfollowing is immediately reflected without waiting for the next fetch.
3. `MessagesScreen` — defence-in-depth filter for zap-only rows and any stale state.

=== Time window

The 30 / 90-day chip on MessagesScreen filters summaries by `lastActivityAt` at render time. It's user-selectable and persists via `AsyncStorage.messages_window_days`. The fetch itself isn't time-bounded (relays return the most recent 500 matching events); the chip just narrows what's displayed.

== Location sharing (snapshot + live, #206)

Two location message types ride on the chat pipeline (NIP-17, or Marmot in a Marmot chat):

- **Snapshot** — a one-shot `geo:<lat>,<lon>` message (the original "Send current location").
- **Live** — WhatsApp-style sharing for a chosen window (15 min / 1 h / 8 h), to a 1:1 chat or a whole Marmot group (#1300). The sender publishes:
  * a *start* marker — a chat message whose text other clients show ("📍 Sharing my live location for 1 h" + a maps link White Noise renders as a map card), with a `live-location` tag carrying `{ sessionId, startedAt, durationMs, first fix }` (and, on NIP-17, the share's session key + update secret);
  * **coordinate updates** on movement (≥ 25 m, ≥ 30 s apart) or a heartbeat when still: in a Marmot chat, kind-20069 MLS application messages; on NIP-17, ephemeral kind-20069 events signed by the session key and NIP-44 encrypted with the update secret — no user signer either way, so Amber / NIP-46 shares run in the background;
  * an *end* marker when the user stops (in the chat, or "Stop sharing" on the notification), the window expires, or the account switches / signs out.

Updates keep flowing with the app minimised or the phone locked: `liveLocationTracker` runs `startLocationUpdatesAsync` (Android location foreground service; iOS `UIBackgroundModes: location`, blue indicator), only needing "While in use". If the provider isn't mounted when the task fires (the OS restarted the process for the task, with no UI), the tracker's headless path sends NIP-17 updates from the persisted sessions (the session key needs no app state). A Marmot share is ended cleanly instead — end marker on the next app open — with a visible "Live location stopped" notice: its updates need the MLS session, and running one outside the app would put a second session over the same MLS store once the UI starts. Expo rebuilds the headless JS runtime for every event, so the headless cadence state is persisted. Receivers feed every update — relay or MLS — into the coalesced `liveLocationUpdateStore` (one flush per ≤150 ms), which the thread bubbles and the Full Map read. Wire details: `PROTOCOLS.adoc` → "Live location".

`parseLiveLocationMarker` classifies a DM as a marker only when the sentinel is the *first non-empty line* (so quoting the header mid-body can't false-positive). Coordinates are required for `start` but optional for `end`: a stop with no GPS fix omits the `geo:` URI rather than fabricate a `0,0` pin, and the parser still recognises the coordless end marker so the receiver bubble flips to "ended".

The sender's session is a small state machine (`src/services/liveLocationStateMachine.ts`): `active → paused → expired → ended`, plus a `stopPending` state so a *failed* end-marker send is retried on the 5 s tick-drain loop until it lands — the peer always learns the share ended. Sessions persist **per active pubkey** (`liveLocationStorage` keys by identity; `LiveLocationProvider` clears state when the Nostr `pubkey` changes or on logout), so a session started under one account can never resume/publish under another.

=== Location-card map

Both location cards render the shared `LibreMiniMap` (OpenFreeMap vector tiles — see _Maps_) rather than a static tile, plotting up to two points:

|===
| Card | Other party's marker | My blue "me" dot
| I share — live | — | yes
| Received — live | profile-circle at their live position | yes (my live position)
| Received — snapshot | profile-circle at the shared point | yes (my live position)

My position is fed from `useUserLocation()`; the peer avatar comes from the conversation's `route.params.picture` (falling back to a `UserRound` silhouette). The card's built-in "Open Map" affordance (`LibreMiniMap.onTapMap`) jumps to the full-screen interactive `MapScreen`. Group location cards currently centre on the shared point only — no me-dot or peer chip yet (follow-up).

*Friends on the full Map.* "Open Map" / `MapScreen` plots **every** friend currently sharing their live location with me, not just the one whose thread I opened. `useFriendsLiveLocations({ enabled })` is the aggregator: it scans the decrypted DM inbox via the pure, unit-tested `collectInboundLiveSessions()` (substring-pre-filtered so a 5 000-row inbox is only fully walked when it changes), filters to inbound shares whose window is still open, watches each session's coordinate updates through the shared `useLiveUpdates` hooks (MLS for Marmot DMs, one bounded relay REQ for NIP-17 session-key and legacy updates, all via the coalesced update store), and resolves each sharer's avatar from contacts / `fetchProfilesForPubkeys`. Friends render through `LibreMiniMap.profileMarkers[]` (circular avatar chips, keyed by pubkey).

== Group Chat (NIP-17 multi-recipient + kind:30200, PR #227)

Client-side group chat layered on top of the existing NIP-17 DM pipeline. No relay-side support is required — every group is just a set of recipients sharing a name, agreed on by the participating clients.

=== Protocol stack

[cols="1,4", options="header"]
|===
| Spec | Role

| https://github.com/nostr-protocol/nips/blob/master/17.md[NIP-17] | Sealed gift-wrapped DMs. The same `nip59.wrapManyEvents` helper sends to N recipients in one call (the helper also wraps a self-copy so the sender syncs across their own devices).
| https://github.com/nostr-protocol/nips/blob/master/14.md[NIP-14] | `subject` tag on the inner kind-14 rumor carries the human-readable group name so the receiver can render it without round-tripping the kind-30200.
| `kind:30200` (custom) | Parameterised-replaceable group-state event. Tags: `["d", groupId]`, `["name", groupName]`, `["p", member]…`. Signed by ANY current group member, not only the original creator. Receivers reconcile by `groupId` + `created_at`. Not a NIP — see `nostrService.ts:GROUP_STATE_KIND` for the schema.
|===

NIP-29 (relay-enforced groups) and NIP-104 (MLS) were both considered. NIP-29 was rejected because it requires opt-in relay support for every member's read relay. MLS was deferred until a maintained RN-friendly library landed; it now ships as Marmot (Alpha) alongside NIP-17 groups — see <<marmot-messaging>>.

1:1 conversations are split by partner pubkey + protocol, with separate inbox rows and timelines. Zaps live in the NIP-17 thread. Dual-published NIP-04/NIP-17 copies appear in both threads. Marmot has its own thread per partner (its 1:1 MLS group). The header protocol picker navigates to the selected thread: NIP-17 is the default, NIP-04 is the legacy option, and Marmot is selectable with an *Alpha* badge (it rides the pre-1.0 `marmot-ts`, which still self-describes as alpha — see <<marmot-messaging>>). The NIP methods are expected to be retired once Marmot is stable.

=== Mentions and read position (#1295)

* *@mentions* (NIP-17 and Marmot groups) — typing `@` in the composer opens a member picker; the composer shows `@Name` while typing and sends a NIP-27 `nostr:npub1…` reference in the text (`utils/chatMentions.ts`). Marmot messages also carry a `p` tag per mentioned member. A mention of you puts an @ badge on the chat row, and an @ button in the thread jumps to the oldest unread mention.
* *Read position* — each 1:1 and group thread, on every protocol, remembers the newest message you've seen (`createdAt` plus id, so same-second messages are placed exactly; `utils/chatUnread.ts`). The thread reopens at an "Unread messages" divider, and the Messages-list badge uses the same rules.

=== Marmot (MLS) messaging — Alpha

Marmot is MLS (RFC 9420) carried over Nostr. The vendored library describes itself as tracking Marmot v2 and wire-compatible with darkmatter; this is not an app interoperability test. White Noise interoperability depends on the client version and protocol profile; no tested version/profile is specified here. MIP labels below are historical cross-references, not conformance claims against the adopted protocol. A user picks *Marmot* in the 1:1 protocol picker or on the group naming step; a 1:1 thread can switch protocol in place. The app uses `@internet-privacy/marmot-ts` behind a small set of adapters (in `src/services/` unless a path is given):

[cols="1,3",options="header"]
|===
| Module | Responsibility

| `marmotCryptoProvider.ts` | Pure-JS MLS ciphersuite `0x0001` (X25519 / HKDF-SHA256 / AES-128-GCM / Ed25519) incl. RFC 9180 HPKE, on the `@noble` libraries. Hermes has no `crypto.subtle`, which both of the library's built-in providers need; `installMarmotCryptoProvider()` also re-points the library's default provider so no fallback path can reach WebCrypto. Verified byte-for-byte against the WebCrypto reference in Jest.
| `marmotSigner.ts` | nsec / Amber / NIP-46 behind applesauce's `EventSigner`, serialised (Amber rejects concurrent Intents). The Nostr key only signs key packages (and their account-identity proof — see "Key packages" below) and seals Welcomes. MLS traffic uses per-message ephemeral keys, so remote signers are not prompted per message.
| `marmotNetwork.ts` | `NostrNetworkInterface` over the shared `SimplePool`: requests resolve on EOSE or 6 s, publishes time out at 10 s, an empty relay list falls back to the lookup relays + `DEFAULT_RELAYS`. Also `createPushTransport()`, the *strict* `PushTransport` for MIP-05 triggers: it publishes only to the relays it is given and reads a server's kind-10050 inbox with no default-relay fallback (looked up on `MARMOT_PUSH_SERVER_RELAYS` first, then the lookup relays; cached 10 min, a miss 1 min).
| `marmotStore.ts` | Every MLS store on one `marmot_kv` table in the SQLCipher DB, partitioned by (owner, namespace) — namespaces in `DATA_STORAGE.adoc`. Values are JSON with `Uint8Array` / `bigint` tagged. Not a rebuildable cache: losing it means being re-invited (also the correct MLS outcome after a backup restore). `deleteMarmotStateForOwner()` wipes an account's rows on per-account sign-out.
| `marmotSession.ts` | One `MarmotClient` per signed-in account: loads and connects every stored group, keeps an unused key package published, and exposes send / create DM or group / invite / remove / rename / leave / accept Welcome. Bounds the library's unbounded kind-445 backfill (see below), replays the last 7 days of each group's durable history on start (an app event is delivered by MLS exactly once, so a message the app died before storing is recovered from there), keeps 500 history events per group, delivers each app event once per group, and creates at most one DM per peer at a time. When several DM groups exist with a peer (they reinstalled and started again), the newest wins.

*Library pin.* The package is a vendored tarball (`vendor/internet-privacy-marmot-ts-0.6.1-pr83.624102f-sigkey.tgz`, `file:` dependency in `package.json`): `marmot-ts` built from upstream PR #83 plus persistent leaf signing keys (#1492) (encrypted media v2 + the `0x800b` media component, live-tested against MDK by its author). Without it White Noise can neither start a chat with a Lightning Piggy user (our key packages wouldn't advertise `0x800b`, which every White Noise group requires) nor show photos in the chats we start. Switch back to the npm release once it ships, and re-check three workarounds then: `spreadProposals()` in `marmotSession.ts` (this build pushes an array-returning proposal action into a commit un-flattened, so remove-member and rename are split into single-proposal actions), the `@ungap/structured-clone` polyfill in `src/polyfills.ts` (Hermes has no `structuredClone`, which the library uses to deep-copy client state), and `alignCommitForMdk()` in `marmotProposals.ts` (this build creates groups with the `app_data_dictionary` extension first, unlike MDK, so metadata commits fork Lightning Piggy and White Noise apart in both directions until the group is realigned; every commit we send, including the founding invite, realigns it, #1309).

*Interop conventions (White Noise).* These describe the adapter behavior, not a guarantee for every White Noise version or feature.

* *1:1 chat* — a two-member group with an empty name where both people are admins (White Noise's DM shape). The app treats an unnamed group of at most two members as a DM, so one mid-creation never shows up as a one-member group.
* *Text* — kind 9, stored as the app's kind 14; the `protocol` column, not the kind, identifies the transport.
* *Photos (MIP-04, `encrypted-media-v2`)* — a kind-9 event with an `imeta` tag, ChaCha20-Poly1305 ciphertext on Blossom, the file key derived from the group's epoch secret. The key can only be *derived* while that epoch's state is retained, so it is derived when the message arrives (one candidate per retained epoch — `imeta` doesn't name the epoch), persisted per message (`mediaKeys:<group>` in `marmot_kv`) so the startup replay can't overwrite it, and folded into the stored row as the `#lpe=1` URL (`alg=encrypted-media-v2`, row kind 15) — the renderer then needs no group state. Those copies outlive the epoch: dropping old epoch secrets doesn't make an already-received photo undecryptable on this device; deleting the row and its `mediaKeys` entry does. Only a public-https Blossom URL that commits to the ciphertext hash is stored. This rejects private address forms, but cannot prevent a public hostname resolving to a private IP or native media redirects reaching one; chat images also use the sender trust gate (see `SECURITY.adoc`). On send, if a commit moves the group to a new epoch during the upload, the photo is re-encrypted and re-uploaded (up to 3 attempts) so a just-added member can decrypt it. Uploads go through `uploadEncryptedBlobToBlossom` (see "Encrypted uploads" below).
* *Reactions* — in a Marmot 1:1 thread a reaction is a kind-7 event (`content` = the emoji, one `e` tag → the message id) and a retraction is a kind 5 with an `e` tag, both sent *inside* the MLS group that holds the target message (not published to public relays). MLS delivers each once, so a reopened thread reads them back from the groups' durable history (`history:<group>`). The action sheet offers six quick emoji plus a "more emoji" grid, and any emoji a peer sends renders as a pill. Marmot group chats have no reactions yet.
* *GIFs* — in Marmot threads and groups a GIF is sent in a White Noise-style envelope: the GIPHY URL, a newline, then `via GIPHY` (`giphyEnvelope()`). The receiver strips an attribution line (`via GIPHY` or `via GIPHY · <creator>`) before rendering the GIF inline.
* *Voice notes (MIP-04)* — sent like photos: encrypted under the group's media key, ciphertext on Blossom, kind 9 + `imeta` (`audio/mp4`, `voice-<ms>ms.m4a`, AAC in MP4, the format White Noise records). Incoming audio attachments play in the normal voice-note player. An attachment the app can't render (video, PDF, or keys it couldn't derive) shows its file name and type, never the URL or keys (#1215).
* *Edits and deletes* — an edit is a kind-1009 app event (one `e` tag naming the original, `content` = the new text), honoured only from the original's author; competing edits resolve latest-wins, as MDK orders them. "Delete for everyone" is a kind 5 inside the group naming the message(s); groups also carry the admin form, kind 4891 (`{"v":1,"action":"remove"}`). The app applies both from White Noise and sends them for your own messages. A quoted reply is a kind 9 with `e` and `q` tags naming the parent, shown with the quoted message.
* *Admins and rename (MIP-01)* — the group's `admin_pubkeys` are shown in group details, and admins can add or remove admins. Only admins can rename a group or change its members (MLS rejects a non-admin's commit), and a group always keeps at least one admin (`utils/groupAdmins.ts`).
* *Several devices per person (historical MIP-06 scope)* — each install publishes a key package in its own `d` slot. Group invites select fresh, valid packages advertising `0x800b` (35 days for White Noise-tagged packages, 14 otherwise), newest per slot, and add at most 10 devices per person after group eligibility checks; when none is fresh, one older valid package is selected as described below. A new 1:1 uses only the newest selected White Noise package if one is present; otherwise it uses the selected devices. Member lists, DM detection and attribution count accounts, not leaves. A new chat invites only the *peer's* devices. An existing 1:1 is topped up (#1559, `marmotDmDeviceSync.ts`): before a send (waiting at most 5 s) and when the chat is opened (once, 3 s after focus; remote signers only warm the lookup), the peer's fresh key packages (no stale fallback) are compared with the group's leaves, and any install with no leaf yet — matched by leaf signature key, plus slots this group was already invited with — is added in one commit through the normal invite path; our own other installs are never added. A White Noise contact gets only their newest White Noise install because released White Noise counts leaves to recognise a DM. Lookups are cached per person for 10 minutes; a failed lookup or commit never blocks the send and is retried after a minute. A declined Amber or NIP-46 device add is suppressed for that chat and key package until the next app start; a new key package can be attempted. Slots matched to existing peer leaves are also remembered to guard subsequent signing-key rotation; background checks never prompt. White Noise packages reusing an invited slot with a different signing key are skipped with a development warning. For this, MLS "same client" is redefined as the same leaf signature key (`marmotSameClient.ts`): the vendored ts-mls default also matched the credential, which in Marmot is the account, so it refused to add, or to accept a commit adding, a second device of an existing member. Linking or pairing your own installs isn't implemented.
* *Devices (#1267)* — a device is an MLS leaf; leaves are grouped into people by credential and identified by their leaf signature key (`marmotDevices.ts`, pure). A Marmot 1:1 shows _Secure chat · N devices_ under the name, opening a read-only "In this chat" sheet; in groups each member has a "_N devices_" list with the app name (the invitation key's `client` tag, from our invite-time record or a bounded relay lookup: at most 8 people, once per 10 min each), when that device's key was made (its account-identity proof) and the epoch it joined. Message info shows *Sent from* (this phone, the app, or "one of N devices": marmot-ts doesn't expose the sender leaf, so a device is named only when certain) and, for your own messages, how many devices *can* read it (Marmot has no per-device receipts). `marmotDeviceTracker.ts` keeps this bookkeeping in `marmot_kv`, gated on the epoch so per-message state changes cost nothing; it never commits or publishes. Grey "joined on N devices" notices are drawn locally and only shown with Advanced → Developer options on.
* *Other app payloads* use the same rumors or text the NIP-17 path builds, carried inside MLS (text changes kind, 14 → 9). Lightning Piggy sends structured NIP-88 polls (1068, votes 1018) in 1:1s and legacy text polls in groups (`useConversationPolls.ts`, `useGroupPolls.ts`); NWC shares, invoices, locations and live-location markers are also app payloads. How another client displays these, including GIFs and polls, depends on that client; White Noise poll support is not established here.
* *Non-message kinds* — deletions (5), reactions (7), MIP-05 push gossip (447–449), edits (1009), agent streams (1200–1202), group-system notices (1210) and moderation (1984, 1985, 4891), which White Noise / Amethyst send into every group, are never stored as chat rows (`MARMOT_NON_MESSAGE_KINDS`). Rows that earlier dev builds stored are purged on start (`deleteMarmotRowsOfKinds`).
* *Not over MLS* — typing indicators stay on their existing public channel. Live-location updates do go over MLS (#1300): kind-20069 app events, kept out of history and rows.

*Key packages* ("invitation keys" in the UI). Kind 30443, published to the account's NIP-65 write relays plus `relay.eu.whitenoise.chat`, `relay.us.whitenoise.chat` and `relay.primal.net` (deduplicated, at most 12 destinations, with space reserved for all three well-known relays) with a `client` tag of `Lightning Piggy` and a `d` slot of 32 random bytes (hex) generated once per account per installation, retained across sign-out (a re-sign-in reuses it instead of minting a ghost slot; two accounts on one install never share one), and reused for every replacement. A kind-10051 list (`relay` tags) advertises these destinations on the same relays and the relay-list indexers. Durable per-account, per-event, per-relay acknowledgement receipts prevent accepted destinations receiving unchanged keys/lists on startup or resume; failed or parked destinations retry the same signed event with backoff; upgrades copy the current signed key, and relay edits update discovery. Publication skips parked relays using `relayHealth`. Failed maintenance uses the existing local-key backoff and appears with a maintenance retry on the invitation-key screen (the separate manual Refresh still rotates the key); remote signers retain their first-use consent rule. Locked test accounts publish and read only the LAN relay, including lists and indexer discovery. To invite someone, the app reads their newest kind-10051 and kind-10002 from bounded lookup/indexer queries, queries kind-10051 destinations first in the target list, then NIP-65 write relays, well-known Marmot relays and remaining lookup relays for kind 30443 (at most 27 destinations, 50 events per relay), keeps the newest event per `d` slot (retired slots skipped), then checks signature, singleton `d` / `i` / `mls_protocol_version=1.0` tags, a lifetime within the 7,261,200 s cap that is current ±1 h, and that the MLS credential matches the author. It selects valid packages advertising encrypted-media-v2 (`0x800b`) whose `created_at` is within 35 days for a `client` tag matching White Noise (case-insensitive, optional whitespace), or 14 days otherwise, newest first. If none is fresh, it selects the single newest compatible package, or the newest valid package if none advertises `0x800b`. For a new 1:1, if the selection includes White Noise, only the newest selected White Noise package is used. The invite batch skips packages rejected by the library's group eligibility or invite checks and adds at most 10 accepted devices per person; rejection makes room for the next selected package (`marmotInvitees.ts`). On start, `ensureKeyPackage()` retires packages with a malformed slot from older builds (NIP-09 delete), *rotates in place* every unused published package that doesn't advertise `0x800b` (same slot, so relays replace it — White Noise requires `0x800b` from every invitee), then makes sure one unused package is published. Each publication is signed twice by the account key: a local-only kind-450 account-identity proof embedded in the MLS leaf, then the kind-30443 event itself. Local keys sign silently; Amber / NIP-46 accounts would be prompted, so they publish only on first Marmot use (creating a chat kicks it off before invitees are resolved, so two remote-signer accounts can still bootstrap a chat) or once they already hold a package. A joined package is spent, so the session publishes a fresh one after each join. Each install's key is refreshed weekly (`KEY_PACKAGE_REFRESH_SECS`), all replaced private key material is deleted immediately after confirmed replacement publication; delayed invites must be retried with the current package, and signing out retires the install's key (NIP-09) (#1210, #1204).

*Welcomes.* Kind 444, gift-wrapped (NIP-59) to the invitee's kind-10050 inbox. They arrive through the NIP-17 inbox paths, so the follow gate applies: only invites from people the user follows are joined, and the invite is also recorded as a row in that person's NIP-17 thread. Each Welcome is joined at most once (`welcomes` marker); a transient failure is kept in `pendingWelcomes` and retried at the next session start, while a permanent one (not for a key package we hold, or malformed) is marked handled.

*Bounded backfill.* `marmot-ts` backfills each group with an unbounded `{kinds:[445], #h}` filter on every connect. The session bounds it: `since` = the newest *ingested* kind-445 minus 10 min of slack, `limit` 500, paged backwards (at most 40 pages) so a device offline through more than one page still gets every commit. The durable per-group watermark only advances once the backfill has been ingested and ignores events dated more than 5 min in the future (anyone can publish a kind 445 with a group's public `h` tag).

*Unreachable peers (NIP-17 fallback).* A 1:1 send to someone with no usable key package — none at all, or only ones this library can't use, such as the legacy MDK 0.8 packages the classic White Noise app (Flutter, store release) still publishes — is offered over NIP-17 instead: the app asks first. Cancel or dismiss sends nothing and keeps the draft; after consent, the thread switches to NIP-17 before the send is attempted, so it stays on NIP-17 even if that send fails. After a successful send, the app attempts a short note saying Marmot was tried, recording it as sent only on success (once per account and peer; `marmotFallback.ts`, `useConversationComposerActions.ts`, #1205). Group creation and adding members have no fallback: they fail with a plain-language error instead.

*Encrypted uploads.* Ciphertext (Marmot photos and NIP-17 kind-15 files) is uploaded as `application/octet-stream`. Media-only Blossom servers — including the default `blossom.primal.net` and nostr.build's free tier — refuse that with HTTP 415, so `uploadEncryptedBlobToBlossom()` tries the user's servers first and then `ENCRYPTED_BLOB_FALLBACK_SERVERS` (`blossom.divine.video`, `blossom.ditto.pub`, `cdn.hzrd149.com`, White Noise's defaults), mirroring only among those. These servers see opaque ciphertext and its hash, never the key.

*Push notifications (MIP-05).* Members gossip encrypted native push tokens inside each group as MLS app events: kinds 447 (token update) and 448 (token list) carry records, 449 carries removals; the payload is `{"v":"marmot-push-v1", …}` with at most 32 entries.

* *What's stored* — `marmotPush.ts` drops any entry that isn't well-formed (a canonical-base64 1,084-byte encrypted token, a fingerprint, the server's pubkey, an `owner_ts` no more than 1 h ahead), isn't for a current leaf of the group, or whose owner signature over the local-only kind-451 proof (bound to the group id) doesn't verify. It keeps one record per (member, leaf, platform, server): an entry wins only with a strictly greater `(owner_ts, SHA-256(SignedRecord))` stamp, and a removal leaves a tombstone so an older record can't come back. `marmotPushNotifier.ts` persists that per group (`pushRecords` in `marmot_kv`), serialised per group, and prunes the records and tombstones of leaves that left on every membership change. We only ever hold *encrypted* tokens — the notification server alone can decrypt them.
* *Triggers* — after a send that at least one relay accepted of a kind 9 (text or photo) or 1068 (poll) — not reactions, deletions, edits or push gossip, matching MDK — the notifier picks every other member's newest record per (member, leaf, platform, server) — so each of a member's devices is woken — groups them by server and gift-wraps kind-446 triggers to the server's pubkey (content = the concatenated encrypted tokens, at most 19 per wrap; tag `["v","marmot-push-v1"]`; fresh ephemeral keys). The server — White Noise's Transponder, for White Noise users — decrypts each token and sends a content-free native push. It runs on a later macrotask and yields between wraps, so it never delays the send, and a failure never affects delivery; one server failing (e.g. a key that isn't a valid curve point, which is also rejected on ingest) doesn't skip the others. On sign-out the notifier is stopped and drained before the account's Marmot storage is wiped, so a late ingest can't re-create records.
* *Publish targets* — the records' relay hints plus the server's own kind-10050 inbox; never a default relay (anywhere else would only leak the trigger). The 10050 is always added because one wrap carries every token for a server: a stale hint on one record (older builds advertised `wss://nos.lol`, which our self-hosted push servers can't reach from their IP) must not strand the records without one. With neither, that server is skipped. Our own servers' records carry no hint, so their relays are a server-side setting (see `architecture/notifications.adoc`).
* *Receive side (opt-in)* — Settings → Security → Push notifications → "Marmot messages", off by default (on Android the background watch already alerts without Google). Apple and Google only deliver pushes sent with the app's own credentials, so each Lightning Piggy app id has its own notification server (a MIP-05 Transponder on `black-panther`): production (`com.lightningpiggy.app`) → `npub1v5lrt4u7vhfnmxwk6c3uepcsrvs4jqyy3z3jrfm5kw73yp0wv2ts5pnwjs`, preview → `npub1rzy2h0rhqmn44tqepvy4h93082878cackvked5lp3wghzkwe3rmsetjeya`; dev (`.dev`) → `npub15vns5zhkr3vq95rg330gmtea6mz2xs24um0hey396nd06p8kfl9say2equ` (APNs sandbox + FCM; only sandbox-signed iOS builds — Simulator, `expo run:ios` — get tokens it can use). Delivery, de-duplication and taps are in `architecture/notifications.adoc` → "Marmot messages and MIP-05 push".
** *Token* — the native token from `getDevicePushTokenAsync` (APNs: hex → bytes; FCM: the UTF-8 string), sealed per MIP-05 "Token encryption" (`marmotPushToken.ts`): fresh secp256k1 ephemeral key, ECDH x-coordinate with the server's even-Y key, HKDF-SHA256 (`marmot-push-token-v1` / `marmot-push-token-encryption`), ChaCha20-Poly1305 over a fixed 1,024-byte padded plaintext → 1,084 bytes. Verified against Transponder's HKDF vector and known-answer vectors from an independent implementation (pyca/cryptography). The token is sealed afresh for each group (the spec-required fingerprint is still the same in every group, so someone in two of our groups can link the records); the raw token is never persisted.
** *Entries* — one kind-447 self-update per group (`["v","marmot-push-v1"]` tag; one entry for our own leaf, `owner_ts` = now in ms, strictly above our previous record), and kind-449 removals. `owner_sig` is the user's signature over the local-only kind-451 proof event; before using a signer's result we check the returned event is exactly the one requested (pubkey, `created_at` 0, kind, tags, content, recomputed id) and that the BIP-340 signature verifies (MIP-05 "external signer" rule). We don't send 447 token requests or 448 list responses (MDK doesn't either).
** *When we publish* (`marmotPushRegistrar.ts`, per account; what was last published per group is kept in `pushShare` in `marmot_kv`) — on enable, on a token change (a newer 447 supersedes the old record by the ordering rule — no 449), on a server or platform change (449 for the old record key, then a 447), and when we join a group or our leaf changes. A group that gained members gets the *same* signed 447 re-sent (its owner proof is still valid), so new members can wake us with no new signature. Turning push off sends a 449 everywhere, then deletes the token at Apple/Google so copies the members already hold go dead (a failed deletion is retried at the next start). Removing an account (whose key is already gone) deletes the token instead of signing removals; a fresh token is fetched once another account's session runs, and that account's groups are re-signed right away as part of the same user action. On iOS a re-registration may return the same APNs token, so revocation there is best-effort (MIP-05 says so too). Our own stamps never go backwards: the highest `owner_ts` we signed per group (`pushShareTs`) survives removals, so a re-enable always outranks our own tombstone. Passes run 3 s after group churn, never before stored groups have loaded, do nothing until the token is known (a slow start can't be mistaken for "off"), and are abandoned — before any further signature or publish — when the session stops or the registration changes.
** *Signer prompts* — one signature per group (the proof binds the group id). nsec signs silently. Amber / NIP-46 are only asked in response to a user action: enabling or disabling (every group, stopping at the first decline), "Finish setup" in Settings (shown with the count of groups still waiting), or sending a message in a group not set up yet (that group only). Background passes never prompt, and a restart re-signs nothing. In Amber, remembering the approval for kind 451 makes later ones silent.

*Known gaps (Alpha).*

* No post-join `selfUpdate()` key rotation yet (the library warns an immediate rotation forks the group).
* Chats created before the media pin carry no `0x800b` component, so White Noise won't send or show photos in them (a new chat does).
* Only the first image of a multi-attachment message renders, and a photo's caption is dropped.
* Classic White Noise users (legacy MDK 0.8) are reachable only via the NIP-17 fallback.
* Invites from senders outside the follow gate are not joined.
* Without the opt-in push (above) — and always on de-Googled Android — Marmot messages raise no alert while the app is closed: the Android background message watch and background detect-and-ping only look at gift wraps (kind 1059), not kind-445 group events.
* Marmot *group* messages are stored in the plaintext AsyncStorage group log like NIP-17 group messages — see `DATA_STORAGE.adoc` → "Threat model".
* Reactions in Marmot groups and a NIP-17 fallback for groups are not implemented.


=== Send path

`sendGroupMessage()` in `NostrContext`:

1. Build a kind-14 rumor with `subject = group.name`, one `p` tag per recipient, content = message text.
2. Call `nip59.wrapManyEvents(rumor, senderSecret, [...recipients])` — produces N+1 wraps (one per recipient + a self-wrap for cross-device sync).
3. `Promise.all(pool.publish(...wraps))` to the union of read+write relays.
4. Optimistically `appendGroupMessage()` locally with a `local_…` id and fire `notifyGroupMessage()` so `GroupsContext` bumps the activity rollup that drives Messages-tab ordering.

NSEC-only path. Amber path requires per-event `signEvent` IPC which the NIP-59 helpers don't expose; tracked as a follow-up.

=== Receive path

The existing NIP-17 decrypt loop (`refreshDmInbox` + per-thread inline decrypt) calls `tryRouteGroupRumor()` for every kind-14 rumor BEFORE the 1:1 DM cache path:

[cols="1,4", options="header"]
|===
| Result | Caller behaviour

| `routed` | Persisted to `groupMessagesStorageService` keyed by viewer + `group.id`; `notifyGroupMessage()` fires; caller continues to the next wrap.
| `group-no-match` | Group-shaped rumor (≥2 OTHER participants) but no locally-known group whose roster matches the participant set. Dropped; caller continues. CRITICAL: caller must NOT fall through to `partnerFromRumor`, which would arbitrarily pick the first p-tag and bucket the rumor as a 1:1 DM.
| `not-group` | 1:1 DM (or malformed). Caller proceeds with the existing `partnerFromRumor` + cache path.
|===

Routing happens via `groupRoutingRegistry.findGroupForParticipants(otherParticipants)` — a module-level set kept in lock-step with `GroupsContext.groups` so the synchronous decrypt loop can resolve membership without going through React context.

=== Group state subscription (kind:30200)

`subscribeGroupStateForViewer` opens TWO concurrent filters on the user's relays:

* `{ kinds: [30200], '#p': [viewerPubkey] }` — groups OTHERS published that include the viewer.
* `{ kinds: [30200], authors: [viewerPubkey] }` — groups the VIEWER published themselves (the kind-30200 builder excludes the signer from `p` tags by spec convention, so a viewer-authored event won't match the p-filter).

Together these cover every kind-30200 the viewer needs to see, including their own renames syncing across devices.

`reconcileFromGroupStateEvent` enforces:

* Conflict resolution by `created_at`: the newer event wins for a given `groupId`.
* Trust gate: only senders already in the group's local `memberPubkeys` (or the viewer themselves) can update an existing group. Prevents a non-member from hijacking the name on the viewer's device.
* New groups (no local entry for the `groupId`) bypass the trust gate and persist regardless of friend-graph — the friend-graph filter applies at *render time* (`visibleGroups`) so kind-30200 events that land before the kind:3 follow-list refresh aren't lost.

The reconciler runs inside React's `setGroups` callback so concurrent inbound 30200 events and local `createGroup` calls don't clobber each other.

=== Friend-graph anti-spam filter (`visibleGroups`)

A group is rendered only if at least ONE other member is in the viewer's follow list (`useNostr().contacts`). Mirrors the 1:1 "Following only" rule. Locked-on outside dev-mode; inside dev-mode the user can flip it via the chip on `GroupsScreen`. See `GroupsContext.visibleGroups`.

Anti-spam check happens at render, not at write — kind-30200 events still persist regardless of friend-graph (see above). Storage cost is bounded by the relay subscription's `#p:viewer` filter, so a spammer can only inflate the viewer's local store if they specifically address the viewer.

=== Leave semantics ("Delete group" button)

The Leave action only removes the group from the viewer's local AsyncStorage:

* No kind:30200 deletion / tombstone is published.
* Other members have NO signal that the viewer left.
* If a remaining member subsequently publishes a kind-30200 that p-tags the viewer (e.g. a rename, or membership change), the viewer's `subscribeGroupStateForViewer` will receive it via the `#p:viewer` filter, the reconciler will see no local entry for the `groupId`, and a fresh local entry will be CREATED — re-adding the viewer.
* If a remaining member just sends a group MESSAGE (kind-14 rumor) without publishing a fresh state event, the viewer's `tryRouteGroupRumor` returns `group-no-match` and the rumor is dropped. So messages alone don't re-add the viewer; only state events do.

This is why the UI says "Leave" rather than "Delete" — it's local-only and other members can still pull the viewer back in via fresh state events. Multi-party deletion would require either a NIP-09 event the receivers honour or a kind-30200 tombstone — tracked as a follow-up.

=== Account scoping caveat

Group lists (`nostr_groups_${pubkey}`, #288) and group-chat history (`group_history_${pubkey}:${groupId}`, #1240) are both per account. Every history read and write passes the active account, so two local accounts in the same group (synthetic NIP-17 rooms, kind-30200 and Marmot groups all share one id across members) never see each other's *new* history (legacy shared logs from before #1240 are copied to every member account), and signing out deletes only that account's logs (`deleteGroupMessagesForOwner` in `wipeAccountCaches`) — a family member's sign-out no longer wipes everyone's chats, which matters because Marmot history can't be re-fetched.

Upgrade path: the old device-wide `group_messages_${groupId}` blobs can't be attributed to one account, so `groupMessagesMigration.ts` copies each one to *every* local account that is a member of the group (its group list — membership-checked for synthetic rooms — or its Marmot state in `marmot_kv`), merging by message id, and deletes the legacy key only after all copies are written. It's idempotent and crash-safe (a re-run converges) and runs once per launch before any group read. A blob no account owns is never shown and is deleted at the next sign-out. Activity rollups are not ownership evidence (pre-#1214 builds leaked one account's rollup into another's key); the first pass deletes all of them once and they rebuild.

=== NIP-171 groups (member side)

A NIP-171 group (protocol rules in `PROTOCOLS.adoc` → "NIP-171 epoch-ticketed groups") shows up in Messages like any other group, with a NIP-171 tag. Its id is `nip171:<group identity pubkey>`.

* *Joining.* Tickets reach our ordinary NIP-17 inbox. `routeNip171Rumor` takes them (and any group rumor that reached us directly) before the DM pipeline would file them as 1:1 messages; `ingestNip171Ticket` validates and stores them as an invitation (`Nip171Invitations`, above the inbox next to Marmot's); only once the user accepts does `nip171Groups` build the group's keys. Decisions (`accepted` / `declined` / `left` with the newest ticket time) live in a per-account record (`nip171Membership`), so a refresh can't bring back a declined or left group.
* *Receiving.* `useNip171Groups` (composed into `GroupsContext`) starts `startNip171Session` 3 s after sign-in: one subscription for kind 1059 `#p` = every current epoch key, bounded by `limit` (no `since`: NIP-59 randomises `created_at`), on our read relays plus each group's kind-10050 relays. Wraps are decrypted with the epoch key, so this works whatever signer the account uses, paced through `createYieldScheduler`, validated (`classifyGroupRumor`) and appended to the shared group message log. A new ticket re-subscribes.
* *Sending.* `useGroupMessaging` asks `nip171Outgoing` for the rumor, the one recipient (the epoch key) and the relays, then sends through the usual signer branch with no self-copy. Files aren't supported yet.
* *Leaving.* Sends the owner a NIP-17 `-` and forgets the group's tickets and metadata.

== Direct Messaging Performance Architecture (Issues #176, #177, #190)

DMs are the most latency-sensitive surface in the app — they're opened repeatedly, and each open has historically required a relay round-trip plus a decrypt loop that could lock the JS thread for tens of seconds on large inboxes. The architecture below was developed over the perf sweep in PR #191 against a 986-message real-world Nostr inbox on a Pixel 8 on 4G. Target: no thread open ever feels "loading" after the first one.

=== Caching layers

The DM pipeline stacks four independent caches — each addressing a distinct failure mode from the pre-cache behaviour:

[cols="1,1,2", options="header"]
|===
| Cache | Scope | What it stores / why

| **NIP-04 plaintext LRU** (`src/utils/lru.ts`)
| Module-level RAM, `max: 1000`
| Event id → decrypted plaintext. Survives screen pops but not process kill. Refresh-then-reopen costs 0 NIP-04 decrypts. Keyed by event id (immutable) so no TTL needed.

| **NIP-17 gift-wrap cache** (`AMBER_NIP17_CACHE_KEY` / `NSEC_NIP17_CACHE_KEY` in AsyncStorage)
| Per-user pubkey, `max: 5000`, separate by signer type
| Wrap id → `{partnerPubkey, fromMe, text, createdAt, wireKind}`. `refreshDmInbox` writes here for every successfully decrypted wrap; `fetchConversation` reads it to skip its own inbox-wide relay fetch (see "Fetch strategy" below).

| **Persisted DM inbox** (`nostr_dm_inbox_v1_<user>`)
| Per-user pubkey, `max: 1000` entries
| Full `DmInboxEntry[]` painted INSTANTLY on Messages-tab mount; relay refresh merges fresh events in the background.

| **Persisted per-peer conversation** (`nostr_dm_conv_v1_<user>_<peer>`)
| Per (user, peer), `max: 500` messages
| Full `ConversationMessage[]` painted within one frame on thread open; relay delta merges in the background.
|===

All four clear on logout (per-user caches are enumerated via `AsyncStorage.getAllKeys()` + prefix match). The plaintext LRU is module-level so its TTL is process lifetime; the AsyncStorage caches persist across cold starts.

=== Fetch strategy

Steady-state: every DM-relevant relay query carries `since = max(cached.created_at) - 120`. The `-120` is Damus's clock-drift pad (see https://github.com/damus-io/damus[`damus/Nostr/SubscriptionManager.swift`] L293-300): relays with slightly-off clocks still return the last 2 minutes of messages so we don't silently miss one. Cold cache (`max = 0`) sends no `since` filter — full history pulled.

Per-peer `last_seen` is persisted alongside the conversation cache; inbox-wide `last_seen` is persisted alongside the inbox cache.

`fetchConversation(peer)` also **skips `fetchInboxDmEvents` entirely** when the NIP-17 wrap cache is populated (#190). Since `refreshDmInbox` (fired on Messages-tab focus with 30s TTL) already pulls every gift-wrap and writes plaintext to the cache, re-entering a thread just filters cached entries to the peer. Removes the largest residual wall-clock cost from thread opens (~6 s → <1 s on the test inbox).

=== Decrypt threading

The serial `for-await` pattern was replaced with `Promise.all(batches of DECRYPT_YIELD_EVERY=15)` with explicit `setTimeout(0)` yields between batches (the `yieldToEventLoop()` helper). Rationale in `src/contexts/NostrContext.tsx`:

[source,ts]
----
/** `await`ing an already-resolved promise only drains the microtask
 *  queue, which still starves UI events — setTimeout(0) returns to
 *  the task scheduler. Yield every DECRYPT_YIELD_EVERY *attempts*,
 *  not successes, so a run of decrypt failures can't infinite-block.  */
----

For nsec, `nip04.decrypt` is pure-JS via `@noble/ciphers` (~1 ms per call on mid-range mobile), so 15 iterations is ≈1 frame's worth of JS. For Amber, each decrypt is an IPC round-trip that already yields implicitly; the explicit yield only adds scheduler respect, not raw throughput.

=== Throttling & focus-defer

- `refreshDmInbox` has a **30 s TTL** (`DM_INBOX_REFRESH_TTL_MS`): calls within the window are no-ops, unless the caller passes `{ force: true }` (pull-to-refresh). Protects against `useFocusEffect` tab-bouncing triggering a full relay + decrypt sweep on every return.
- All three `useFocusEffect` refreshes (Home's `refreshProfile`, Messages' `refreshDmInbox`, Friends' `refreshProfile`) are wrapped in `InteractionManager.runAfterInteractions(...)` with `.cancel()` on cleanup so the tab-transition animation finishes before the refresh claims the JS thread.
- `fetchConversation` checks an `isMountedRef` before firing `setMessages` / `setLoading` so back-press during a cold fetch doesn't commit state on an unmounted screen.

=== Instant paint pattern

ConversationScreen's `load()` callback reads the per-peer persisted cache FIRST, does `setMessages(cached)` synchronously (paint within a frame), `setLoading(false)`, THEN awaits the full `fetchConversation(peer)` which may spend seconds on a relay round-trip. Whichever result arrives first — cache or relay — is painted; the relay path overrides when it finishes.

Cribbed from Arcade's `arclib/src/private.ts` + `DirectMessageScreen.tsx` `db_only=true` pattern.

=== Relay coverage

Every DM-relevant `fetch*` in `src/services/nostrService.ts` merges the user's own read-relays (from their kind-10002 NIP-65 event) with `DEFAULT_RELAYS`:

[source,ts]
----
const allRelays = [...new Set([...relays, ...DEFAULT_RELAYS])];
----

This deliberately over-fetches so users with a sparse kind-10002 (e.g. a single-relay declaration) still see messages that landed on more popular relays. `DEFAULT_RELAYS` currently = `damus.io` / `primal.net` / `ditto.pub` / `coinos.io` / `nos.lol` (see `src/services/nostrRelayDefaults.ts`).

=== Perf instrumentation

Two log lines emitted unconditionally (not `__DEV__` gated) so they can be grepped from production APK logcat:

- `[Perf] fetchConversation(<peerShort>): <ms>, k4=N (hits=A, fresh=B), k1059=M (hits=C, fresh=D, skippedFetch=bool), since=T, cached=X, merged=Y`
- `[Perf] refreshDmInbox: <ms>, k4=N (hits=A, fresh=B), k1059=M, since=T, fresh=Z, merged=Y, rendered=R`

Breakdown lets us confirm cache-hit behaviour on a real device without attaching a debugger.

=== Known limitations / future work

- A newly-arrived wrap that `refreshDmInbox` hasn't pulled yet (≤30 s ago) won't surface in `fetchConversation` until the next inbox refresh — acceptable for chat UX where "latest" rarely means "last second."
- `pool.querySync` is still one-shot — real-time message arrival requires pull-to-refresh today. Filed as #188 (persistent relay subscription, architectural ~4 h).
- BitmapFactory exception flood on unsupported avatar formats contributes to GC pressure on the Pixel. Filed as #189.
- `react-native-mmkv` swap for the DM-cache AsyncStorage reads/writes would be ~100× faster at scale; marginal at current inbox sizes. Deferred.

== BTC Map dataset

=== Why v4 (and why not bbox)

V3's `/places?bbox=…` endpoint was removed; v4 returns only `{id}` by default and requires an explicit field list with source prefixes (`osm:payment:lightning`, etc.) — see https://github.com/teambtcmap/btcmap-api/issues/52[teambtcmap/btcmap-api#52]. We pull the full global list **once per week** with the explicit field list in `V4_FIELDS` (`btcMapService.ts:28`) and filter client-side. Trade-off: ~6 MB JSON download once per week vs the alternative of issuing a fresh fetch on every viewport change.

=== Caching shape

* In-memory mirror + a single AsyncStorage blob keyed `@btcmap:places-v1`.
* `DATASET_TTL_MS = 7 days`. After expiry the next viewport fetch refreshes; pull-to-refresh on the Explore hub force-refreshes immediately.
* Hydrate is kicked at module-import time so a navigation tap that lands on PlacesScreen can `peekDatasetSync()` and paint within a frame.

=== ±2° bbox widening (fix in `ffd63a4`)

The mini-map's `onBoundsChange` emits the current viewport bbox. Naive filtering (rows whose `lat/lon` falls inside the exact bbox) feels broken when the user zooms out — markers appear before list rows because MapLibre's marker layer paints the moment merchants enter the canvas, but a tight bbox excludes anything not strictly inside. The fix widens the filter bbox by ±2° (roughly ±220 km at UK latitudes) so the list mirrors what the user actually sees as "the area I'm exploring". See `ffd63a4 fix(places + explore): widen merchant bbox to ±2° so zoom-out actually loads` (originally landed on Leaflet, behaves identically on MapLibre because both emit the same `lat/lon` bbox).

== NIP-GC + NIP-52 cache layer (`nostrPlacesStorage`)

Mirrors the BTC Map pattern:

* **Two AsyncStorage keys** — `@lp:nostr-caches-v2` (kind 37516) and `@lp:nostr-events-v1` (kind 31923).
* **In-memory mirror** + sync peek so the first useState init in HuntScreen / EventsScreen has populated data on warm starts.
* **Capped at 500 entries each** — newest by `createdAt` for caches, newest-upcoming by `startsAt` for events. The blob is well under 200 KB at the cap.
* **7-day TTL** on the persisted blob; the live relay subscription (`subscribeNearbyCaches` / `subscribeNearbyEvents`) authoritatively backfills as soon as the user lands on the rail.
* **Write-through replace**, fire-and-forget. The in-memory state stays authoritative for the current session — a failed AsyncStorage write doesn't pollute the rendered list.

This is the same pattern PR #508 used for NIP-17 DM wrap IDs (paint cached state instantly, let the live sub update in place).

=== Bbox-driven list filter

The mini-map on Places / Hunt / Events emits `{minLat, maxLat, minLon, maxLon}` whenever the user pans or zooms. The host screen filters its list against that bbox. UX consequence: zooming out reveals more rows; zooming in narrows them. Pairs with the "within X km radius" chip — bbox is the primary filter, radius is the secondary cap.

== `usePubkeyProfile` hook

Reusable kind-0 lookup with layered caching:

. **In-memory `zapSenderProfileStorage`** — already populated for any pubkey the wallet has ever seen as a zap sender or contact.
. **AsyncStorage fallback** — `zapSenderProfileStorage.get(pubkey)` reads from disk on miss.
. **Relay fetch** — `nostrService.fetchProfile(pubkey, readRelays)` unions the user's NIP-65 read relays with `PROFILE_RELAYS` (purplepag.es / user.kindpag.es / primal.net / damus.io / nostr.land). Result is written back to the cache.

Consumers (hider chip on `HuntPiggyDetailScreen`, finder chip on each find-log row, organiser row on `EventDetailScreen`) all resolve instantly for any pubkey the user has interacted with before, and degrade gracefully to a pubkey-prefix fallback when neither cache nor relay yields a name.

== `useNearbyRadius` shared setting

A single AsyncStorage key (`@lp:nearby-radius-v1`) holds the user's preferred "within X km" radius. Default is 50 km; options are 5 / 25 / 50 / 250 km + "anywhere" (null). Every screen that surfaces a "nearby" affordance — the home rail, PlacesScreen, HuntScreen, EventsScreen, distance chips on geo-cache rows — reads through `useNearbyRadius()` so a change on one screen propagates everywhere on the next render.

== Pre-seed on first render (`5776fcc`)

A naive `useState([])` on Explore / Hunt / Events would paint a blank rail for one frame even when the in-memory mirror is populated. Each list screen now seeds its initial state via `peekCachedCachesSync()` / `peekCachedEventsSync()` / `peekDatasetSync()` so the first paint already shows real rows. The live sub then overwrites in place as fresh events land.

== Offline cold-start test (`scripts/test-offline-cold-start.sh`)

End-to-end guard that the cache layers above actually paint without network:

. Shell wrapper disables Wi-Fi + mobile data via `adb shell svc wifi disable` / `svc data disable`.
. Force-stops the app and cold-launches it.
. Runs `.maestro/authentication/flow-009-offline-cold-start.yaml` which asserts every cached surface (Home tx list, Friends, DM inbox, Explore hub, Places list, Hunt list, Events list) paints within the Maestro default timeout.
. `trap` restores network whether the flow passes or fails — a regression doesn't strand the device offline.

Pre-req: the app must have been opened at least once on the device with network, so BTC Map + NIP-GC + NIP-52 caches are on disk. Run nightly on the AVD; spot-checked on the Pixel before each prod release.

=== NTAG21x tag locking (Hide-a-Piglet)

Written tags carry a reversible PWD/PACK lock so a passer-by with an NFC writer can't repoint the prize link. The wizard's step 6 "Lock the tag" toggle (default on) runs the Android write path under `NfcTech.MifareUltralight` so we can chain (a) NDEF user-data pages, (b) PWD/PACK page writes, (c) ACCESS + AUTH0=0x04 in one tap. Configuration / PWD / PACK page addresses are chip-specific (NTAG215 lives at 0x83-0x86, NTAG216 at 0xE3-0xE6, NTAG213 at 0x29-0x2C and rejected at runtime for being too small for the payload); a GET_VERSION-based dispatcher picks the right `NtagPages` config before any write. The 4-byte PWD surfaces as an 8-hex-char PIN on step 6 (post-write reveal-on-tap) and gets persisted onto the matching `HiddenPiggy.nfcLock` in SecureStore so Edit-this-Piglet re-hydrates the same PIN.

Re-writes are smart: when the wizard has stored secrets for the Piglet, the write path sends PWD_AUTH first, writes the new NDEF, and re-applies ACCESS + AUTH0 idempotently — the same PIN keeps working post-rewrite without the hider tracking a fresh one, even on a chip whose AUTH0 had been reset to 0xFF while PWD/PACK stayed in place. The Unlock-tag button on the PIN card opens `NfcUnlockSheet`, which authenticates then flips AUTH0=0xFF to disable protection. Pure-logic byte builders + 33 unit tests live in `src/utils/nfc/ntag21xLock.ts`; the device-bound transceive (including the GET_VERSION family dispatcher, the capacity guard, and the post-failure lock-state diagnostic) lives in `src/services/nfcService.ts → writeNdefBytesAndLockAndroid + unlockHuntTag`. The single-record private-Piglet writer (`writeLnurlToTag`) routes through the same helper when the toggle is on. iOS keeps the unlocked Ndef path (no CoreNFC lock primitive in the lib today). Issue #567.

= Market (Explore → Market)

The Market lists physical goods sold for sats, and lets anyone with a signer sell their own. It speaks the https://github.com/GammaMarkets/market-spec[Gamma Markets] profile of NIP-99, which the reference shops (RobotechyShop, edenweeks.art) publish, so a listing made here is readable by other Gamma storefronts and vice versa.

== Buying

* *Sources* — "Lightning Piggy preferred sellers" (the default), "WoT: Friends" (listings from people you follow), or, with experimental features enabled, "Friends of friends" (your follows plus their follows) and "All" (queries without an author filter; results are bounded and spam-curated). `marketListingsService.ts` takes a bounded, signature-checked snapshot of kind-30402 products (and legacy NIP-15 kind 30018) on `MARKET_RELAYS` plus your read relays, applies sellers' NIP-09 deletions, and skips `visibility: hidden`. Filters: ships to, currency, merchant. *Ships to* is derived only from sellers' published data (`utils/marketShipsTo.ts`): each listing's `shipping_option` refs are resolved to kind-30406 options in batched, cached queries (`services/marketShippingCache.ts`) and their `country` / `region` tags give the destinations; worldwide options and `digital` listings match every country, and curated or unresolvable listings are "shipping unknown" (kept unless "Include listings without shipping info" is switched off). Country names come from a CLDR table (`data/countryNames.json`, `scripts/generate-country-names.mjs`) because Hermes has no `Intl.DisplayNames`.
* *Product page* (`MarketProductDetailScreen` / `MarketListingDetails`) — photos, price, stock, category chips, the seller's Nostr name and avatar, and a shipping list: the seller's kind-30406 options (any app's, with country names accepted as well as codes) priced with the product's per-item `extra-cost` (`utils/marketListingShipping.ts`). If referenced options can't be found it re-checks once, then says "Shipping: ask the seller" (also shown when a listing references no shipping options and isn't digital, and for curated catalogue items). Pull to refresh.
* *Markdown descriptions* — NIP-99 `content` is Markdown. `utils/marketMarkdown.ts` runs the `marked` lexer (pure JS, no native module) and maps a whitelisted subset onto `<Text>` / `<View>`: paragraphs, bold / italic / strikethrough, headings, lists, block quotes, code, and https links, which ask before leaving the app. Raw HTML and images are dropped; long descriptions collapse behind "Show more".
* *Feedback* — reviews are Gamma kind 31555 (addressable, `d` = `a:30402:<seller>:<d>`, ratings stored 0–1 and shown as stars); comments are NIP-22 kind 1111 rooted on the product (`utils/productComments.ts`). You can edit or delete your own; deletes are NIP-09 and only count when the deleter wrote the original (`utils/nip09.ts`). No review form on your own listing.
* *Checkout* — choose shipping and quantity, then a kind-16 `type 1` order rumor is gift-wrapped (NIP-17) to the seller (`utils/marketOrder.ts`). The seller's kind-16 payment request (`type 2`, an invoice to pay), status and shipping updates (`type 3` / `4`) and kind-17 receipt show in that conversation, and the invoice is paid from your wallet (`utils/orderEvents.ts`).

== Selling: My shop (#1273)

A store button in the Market header opens *My shop* (`MarketMyShopScreen`), a hub (#1534). It has the merchant's profile card (with *Edit Profile*), then one grouped card of sections, each showing a live summary, then the primary *Sell an item* button:

* *Currencies* (`MarketShopCurrenciesScreen`) — the shop's default currency. Gamma has no shop currency, so it stays on this phone (`sellerPreferences`) and prefills new listings and shipping options. A "Receive payments to" wallet setting will sit here too.
* *Shipping options* (`MarketShopShippingScreen` + `ShippingZoneEditor`) — up to 10 kind-30406 options, each with a name, a cost and the countries it ships to (quick picks Worldwide / UK / EU / US & Canada, or any country). The form only loads from a completed relay fetch, and every save checks each option's current revision first (fail closed).
* *Collections* (`MarketShopCollectionsScreen`) — create / edit / delete kind-30405 collections, and remove the legacy "shop" collection older versions wrote.
* *Listings* (`MarketShopListingsScreen`) — *Your listings*, with Edit, Preview (the real product page, with a banner) and Delete.
* *Orders* (`MarketShopOrdersScreen`) — incoming kind-16 orders for the seller's own listings, read from the encrypted DM store (`dmDb.getShopOrderRows` → `utils/shopOrders.ts`). It adds no relay subscription. Tapping an order opens the buyer's NIP-17 conversation at that order.

*Sell an item* (`MarketListingEditorScreen`) takes photos (EXIF-stripped, uploaded to Blossom; the first is the cover, and photos can be reordered), title, Markdown description, price and currency, stock, collections (chips, plus a *New collection* popup), physical or digital, which shipping options apply (each with an optional extra cost) and categories. A physical item needs at least one shipping option. If the shop has none, *Sell an item* asks the seller to add some, or to say the item is digital, and the editor won't publish a physical listing until one exists (`utils/shopSellGate.ts`). A failed fetch counts as unknown, never as "no shipping options".

[cols="1,3",options="header"]
|===
| Event | What we publish

| 30402 product | `d`, `title`, `price [amount, currency]`, `type [simple, physical\|digital]`, `visibility`, `stock`, `image [url, "", order]` per photo, `t` per category, `shipping_option [30406 coord, extra-cost?]`, `a` → the shop, `published_at`; description in `content`.
| 30406 shipping option | One per zone: `d`, `title`, `price [cost, currency]`, `country [ISO alpha-2…]`, `service standard`. Worldwide omits `country` (the spec has no worldwide value; readers treat an absent tag as worldwide).
| 30405 shop | `d = lightning-piggy-shop`: `title`, description in `content`, `a` → every product, `shipping_option` → every zone, plus a `currency` tag (a Lightning Piggy extension; other clients ignore it).
| 5 deletion | NIP-09 with `a` + `e` + `k` for a removed listing or zone; the listing is hidden locally until relays catch up.
|===

*Never a blind overwrite.* Before every save, `marketSellerService.ts` fetches the current revision of the seller's own events, asking each relay separately and trusting the answer only with a *quorum* (at least half the healthy relays completing). Without a quorum nothing is published ("Couldn't load your shop. Try again."), so a relay timeout can never read as "no shop". If a newer revision exists than the form was loaded from, the user is asked before overwriting, and the save builds on that newer revision so tags other clients added survive. Every fetched "own" event is signature- and author-checked before it can become the base of an edit. Edits republish under the same `d` with a strictly newer `created_at`. Publishing goes to at most 8 write relays with a 12 s deadline and only counts as done when a relay acknowledges it (an unreachable relay is a rejection, `nostrEventPublish.ts`, #1347), and signs through `useNostr().signEvent` (nsec, Amber or NIP-46). A per-account snapshot (`sellerEventStore.ts`, persisted, wiped on sign-out) lets *My shop* paint at once after a cold start.

Pure logic lives in `src/utils/` (`marketSellerEvents.ts` build/parse, `marketSellerSnapshot.ts`, `marketSellerRevision.ts`, `marketListingShipping.ts`), relay I/O in `src/services/marketSellerService.ts`. Out of scope so far: order handling for your own listings (#1290), drafts and variants (#1293).

=== Listing relay coverage and republishing (#1603)

*My shop → Listings* checks kind-30402 coverage on focus and cancels on blur.
`listingRepublish` queries each relay once with the seller's author and all displayed
listing identifiers, bounded to at most 1,000 events per relay. Targets are the
union of NIP-65 write relays and `MARKET_RELAYS`; test-account lockdown resolves
that union to the LAN test relay only. No age cutoff is used because an old
listing can still be the latest revision. React receives one combined snapshot.

`listingRelayCoverage` counts relays holding the newest verified version (same id
or same/newer timestamp at the same address). A warning means fewer than two
copies, or fewer than every relay when there are only one or two targets.
*Republish* verifies the existing signature and author again, skips targets already
holding that revision, and reports each relay's acceptance, rejection reason or
lack of response. It never invokes a signer. *Republish all* processes listings
sequentially with the shared yield scheduler and presents one summary.

When no valid signed copy exists locally or on the queried relays, the row offers
*Re-sign and publish*. After a branded confirmation, `useSellerActions.resignListing`
checks the current revision and re-signs the stored event's kind, content and tags
directly, without a listing draft round-trip. Newer revisions, deletions and failed
revision queries prevent signing. This path requires one signer approval. The bulk
action skips missing copies instead of asking to sign.


= Languages (i18n)

Nine locales: `en` (source of truth), `de`, `es`, `hu`, `pl`, `uk`, `hi`, `mr`, `zh-Hans` (`SUPPORTED_LOCALES` in `src/i18n/index.ts`, catalogues in `src/i18n/locales/`). The language is chosen per account (Account → Display & language, or "System"), and device-locale detection uses the full language tag (`zh`, `zh-CN`, `zh-Hans-*` → Simplified; Traditional Chinese also gets Simplified until a catalogue exists). English is the fallback for any missing key.

* *Plurals* — Hermes has no `Intl.PluralRules`, so each catalogue gets its CLDR cardinal rule from `make-plural` (`src/i18n/plurals.ts`). `requiredPluralCategories(locale)` is the single source of truth for which forms a catalogue needs (pl and uk need `one` / `few` / `many` / `other`), shared by the app, the catalogue guard and `i18n:sync`.
* *Numbers and dates* follow the app language, not the device locale (`useLocale().formatLocale`; background code reads the committed app locale). `hi` and `mr` are pinned to Western digits with Indian grouping (`12,34,567`).
* *Tooling* — `npm run i18n:sync` lists missing, stale and *reworded* strings (English changed since `git merge-base HEAD origin/main` while the translation didn't), drafts them with the developer's own `claude` or `codex` CLI (`--draft`), and merges them back with validation (`--apply`); `--check` fails while anything is out of date. Rules for translators: `i18n/GLOSSARY.md`.
* *Pseudo-language* — `en-XA`, "Pseudo (testing)", generated at runtime from `en.json` in dev and preview builds only: every string accented, about 40 % longer and bracketed, so clipped or hard-coded text stands out.
* *CI guard* — see `TESTING.adoc` → "Translations".
