= Performance measurement

This guide covers how to measure Lightning Piggy's runtime perf, what the
output means, and how to feed it to Stevie (the perf agent — *Stevie the
Speedster* from the T-Minus-15 plugin; see "Stevie's project notes" below).

Scope: **dev-time only.** Lightning Piggy targets privacy-centric users
(GrapheneOS / degoogled Android) so we never ship commercial telemetry —
no Sentry, no Datadog, no Firebase Performance. Everything here runs on
your own device and your own machine.

== Quick start

[source,bash]
----
# 1. Set the emulator GPS so location-aware screens have a fix.
#    Longitude first (gotcha), latitude second:
adb emu geo fix 0.0589 52.2964   # Longstanton, near a cached merchant

# 2. Run the Explore cold-start measurement, 5 samples:
bash scripts/perf-explore-cold-start.sh 5

# 3. With a Perfetto trace on run 1 (if you want to see *where* the time goes):
PERFETTO=1 bash scripts/perf-explore-cold-start.sh 5
----

== What the scripts report

=== Wall-clock distribution

Every `scripts/perf-*.sh` now emits a six-line block via the shared
`scripts/lib/perf-stats.sh` helper:

[source]
----
Cold-start wall-clock (n=5):
  min   4830 ms
  p50   5210 ms
  p95   6240 ms
  p99   6890 ms
  max   6890 ms
  mean  5430 ms
----

**Always read p99/max, not mean.** A mean of "24 s" can hide a 38 s
outlier — and outliers are the user-visible regression. Means are
provided for trend-tracking, but the actionable metric is p99.

=== Frame jank (per run)

Each run prints a `gfxinfo:` line right after its wall-clock:

[source]
----
run 1: 5230 ms — gfxinfo: total=387 janky=12 (3.1%) p50=8ms p95=15ms p99=24ms
----

[cols="1,3", options="header"]
|===
| Field | Meaning

| `total`
| Frames rendered during the run. Higher = more on-screen activity.

| `janky` (count and %)
| Frames that took >16.67 ms (60 Hz) to commit. **>5%** is noticeable to
the user; **>10%** is bad.

| `p50`
| Median frame time. Should be well under 16 ms on a healthy screen.

| `p95` / `p99`
| The tail. A p95 of 60 ms means 1 in 20 frames stuttered for ~4 frames
worth — visible jank.
|===

=== Perfetto trace (optional, `PERFETTO=1`)

When `PERFETTO=1` is set, the first run captures a 40 s system trace
covering the scheduler, gfx + view + input atrace categories, and the
target app's atrace events. Output:

[source]
----
perfetto: pulled to /tmp/explore-cold-start-trace-194233.pftrace — open at https://ui.perfetto.dev (drag-drop the file)
----

Drop the `.pftrace` on https://ui.perfetto.dev. You can then:

- See per-thread CPU usage during the freeze (look for the JS thread)
- Spot the long `setState` commit blocks
- Confirm whether jank lives in the JS thread, the native bridge, or GC

This is the canonical way to diagnose a freeze — wall-clock alone never
names the culprit.

== Per-screen markers via `[PerfTab]`

`src/utils/perfLog.ts` exposes four bracketing markers around a tab
switch. Two of them are emitted automatically by `AppNavigator.tsx`'s
tab listeners; two are emitted by the destination screen itself.

[cols="1,2,1", options="header"]
|===
| Marker | When | Source

| `[PerfTab] <tab> tap`
| `tabPress` event fires on the bottom tab button — closest thing to "user touched the screen".
| `perfTabTap(name)` in the tab `listeners`.

| `[PerfTab] <outgoing> hidden tap→hidden=Xms`
| The blur event on the previously-focused tab landed. Brackets the navigation transition itself, so a slow `tap→hidden` means the animation is janking (not the destination).
| `perfTabHidden(name)` in the tab `listeners` `blur:` handler.

| `[PerfTab] <tab> focus tap→focus=Xms`
| React Navigation completed routing to the new screen. Equivalent to "screen mounted / re-focused". Often very fast (under 200 ms) even when content is nowhere near ready.
| `perfTabRendered(name)` in the tab `listeners` `focus:` handler.

| `[PerfTab] <tab> ready tap→ready=Xms (detail)`
| The destination screen judges its own content as usable. Deduplicated per tap so re-renders don't pollute the log.
| `perfPageReady(name, detail?)` called from the destination screen — typically in a `useEffect` keyed off the first non-empty primary dataset.
|===

A healthy tab-switch reads:

[source]
----
[PerfTab] Home hidden tap→hidden=120ms       ← old screen out
[PerfTab] Explore focus tap→focus=180ms      ← new screen mounted
[PerfTab] Explore ready tap→ready=420ms (10 merchants)
----

A degraded tab-switch (real example from #31 pre-fix on a Pixel 8):

[source]
----
[PerfTab] Explore focus tap→focus=193ms
[Perf] heartbeat #199 gap=7992ms             ← JS thread blocked 8s
[PerfBlock] fetchCachesByAuthor: 4 events in 9402ms
[PerfBlock] ExploreHome fetchPlacesInBbox: 10692ms places=367
[PerfBlock] ExploreHome fetchPlacesInBbox: 11762ms places=367   ← second fetch!
                                              (GPS-jitter cascade)
----

Focus event fired in 193 ms — fast — but `ready` would have come ~22 s
later because the rail's `setMerchants` hadn't fired yet. **That's the
gap between "screen is on" and "user can do something". Both numbers
matter.**

== Patterns to avoid

These are concrete shapes that have caused user-perceived freezes in
this codebase. Each one has a static test (greppable) and a runtime
test (a marker that flares).

=== GPS-jitter cascade (issue #31)

**Shape:** a `useEffect` with `[pos]` (or another rapidly-changing
context value) in its dep array kicks an async fetch. Android emits
position samples ~1 Hz, each as a fresh `{lat, lon}` object — even
when the user is sitting still and the lat/lon are byte-identical
to the previous sample. React compares deps by reference, so the
effect fires on every sample. Each fire spawns a new in-flight
fetch; the previous one's Promise doesn't yield once it starts
processing the response. They stack.

**Symptom:** "first few clicks OK then really slows down" — the JS
thread queue grows with each tab focus until it can't paint frames.
`gfxinfo` collapses to single-digit frame counts per switch.

**Fix:** derive a *bucketed* identity for the dep — round lat/lon to
3 decimal places (~100 m) via `useMemo`, key the effect on that.
Two samples that round to the same bucket = no re-fire. See
`ExploreHomeScreen.tsx`'s `posBucket` for the canonical
implementation. PlacesScreen / MapScreen don't need this — they
have an actively-panned map where every metre matters.

**Static test:** `grep -nE "useEffect\\(.*\\[.*pos.*\\]"` across screens.
Anything matching deserves a bucket.

=== Country-sized BTC Map bbox queries (also #31)

**Shape:** `fetchPlacesInBbox({ minLat: pos.lat - 2, maxLat: pos.lat + 2, … })`
covering a ±2° rectangle returns 300-400 merchants the screen only
ever shows ~10 of. Network payload is large, post-response
`Array.map(reshape)` blocks the JS thread for 5-8 s synchronously,
every MapLibre marker becomes a `<Marker>` element React has to
reconcile.

**Fix:** **tiered nearest-N** via `fetchNearestPlaces(lat, lon, 10)`
(see `src/services/btcMapService.ts`) — walks radii 25 → 100 → 500 km
until at least N results come back. Urban callers do one ~10 KB
round-trip; rural callers walk further. Pair with an
anchor + time SWR short-circuit so repeated tab focuses inside an
hour, within 5 km, don't hit the network at all. Only use on
surfaces where the map is decorative; PlacesScreen / MapScreen keep
the bbox call.

=== `Array.prototype.shift()` as a FIFO eviction on a large array

**Shape:** a bounded cache holds N entries in an array, with a Set
keyed by the same value for O(1) membership tests. On insert past N,
the code calls `array.shift()` to evict the oldest entry. This was the
original implementation of `nostrService.ts`'s `verifiedEventIds` cache
— PR #628 review flagged it as O(N) per eviction once the cache fills,
because every remaining element has to be re-indexed.

**Symptom:** the cache itself was meant to *save* JS-thread time
(skip schnorr re-verification). With `shift()` on a 10 000-entry array,
the eviction cost ate into the savings — measurable on the same hot
path the cache is supposed to speed up.

**Fix:** circular buffer + head cursor:

[source,ts]
----
const CAP = 10_000;
const ids = new Set<string>();
const order = new Array<string | null>(CAP).fill(null);
let head = 0;
const remember = (id: string): void => {
  if (ids.has(id)) return;
  const evicted = order[head];
  if (evicted !== null) ids.delete(evicted);
  order[head] = id;
  ids.add(id);
  head = (head + 1) % CAP;
};
----

Both insert and evict are O(1). The initial `null` slots evict harmlessly
during the warm-up window (Set.delete on null is a no-op). Resetting the
cache is `ids.clear(); order.fill(null); head = 0;`.

**Static test:** `grep -nE '\.shift\(\)' src/` and inspect each — most
hits in this codebase are legitimate one-shot dequeues; the dangerous
shape is `.shift()` inside the same function as a matching `.push()`
when both run on a high-frequency callback.

=== Per-tab Maps keyed by `tabName` for transient state

**Shape:** a `Map<string, T>` keyed by tab name, populated on tap, never
cleaned. Once the user has visited Home, Messages, Explore, Friends,
the Map has 4 permanent entries. Any consumer that iterates the Map on
a frequent event (e.g. an outgoing-tab blur listener that wants to
emit "tap→hidden") then logs / processes one entry per tab visited.

This was the original `__tabTapAt` in `perfLog.ts` — PR #628 review
flagged it for accumulating stale entries.

**Fix:** track the most-recent value as a single pair of variables
rather than a Map. Only one tab transition is ever in flight at a time
(React Navigation serialises tabPress / focus / blur per gesture), so
the Map's invariants are stricter than its type — collapse to scalars:

[source,ts]
----
let __lastTapAt: number | null = null;
let __lastTapDestination: string | null = null;
----

`perfTabTap` writes both, `perfTabHidden` / `perfTabRendered` / `perfPageReady`
read both. No leak by construction.

**Static test:** `grep -nE 'new Map<string,' src/utils src/contexts` and
ask "does this Map ever shrink?" If the answer is no AND the key space
is finite AND only the latest matters, scalarise.

=== console.log left on a per-event hot path

**Shape:** a `console.log` inside a Nostr `onevent` callback or a
streaming response handler. Each emission costs ~0.5-2 ms of
formatting + IPC to the native bridge. 150 profile events on cold
start = 75-300 ms of pure log overhead.

**Fix:** guard with `if (__DEV__)`. The repo's `EXPO_PUBLIC_KEEP_PERF_LOGS`
flag re-enables them when needed, but the default release path is
stripped via `babel-plugin-transform-remove-console`.

== Capturing logcat during a perf script (real device)

Perfetto can't see system-level events on a "user" Android build
(see TROUBLESHOOTING). For real-device JS-thread attribution,
combine `adb logcat` with the perf script:

[source,bash]
----
adb -s "$SERIAL" logcat -c
adb -s "$SERIAL" logcat -v time '*:S' ReactNativeJS:V > /tmp/run.logcat &
LOGCAT_PID=$!
sleep 1
PIGGY_DEVICE="$SERIAL" PIGGY_APP_ID=com.lightningpiggy.app.preview \
  scripts/perf-explore-tab-switch.sh 8
sleep 3
kill $LOGCAT_PID
grep -E "\\[PerfTab\\]|\\[PerfBlock\\]|\\[Perf\\] heartbeat gap=[0-9]{3,}" /tmp/run.logcat
----

The `[Perf] heartbeat gap=` filter narrows to gaps ≥100 ms — every
synchronous JS-thread block that lasted longer than a frame budget.
Pair with a per-iteration screenshot loop (see `TROUBLESHOOTING.adoc`'s
"Tab-switch perf script reports 20-30 s..." entry) to confirm whether
the freeze is real or a Maestro artefact.

== Methodology

Stevie owns the deeper methodology — the T-Minus-15 plugin agent carries
the 12-category audit (JS-thread blocking, per-event setState, context
re-render cascades, subscription lifecycle, etc.). The short version:

1. **Measure** before changing anything. Wall-clock + gfxinfo + a
   Perfetto trace = three independent angles on the same problem.
2. **Audit** the code path implicated. Static analysis often beats
   adding more instrumentation — every category in Stev.ie's
   methodology has a "grep for it" form.
3. **Fix one thing at a time.** Don't ship a 5-issue bundle. Measure
   after each.
4. **Verify** with a fresh measurement. If p99 didn't move, the fix
   didn't move the needle.

== Adding a new perf script

Use this skeleton — it inherits the stats + gfxinfo + Perfetto helpers:

[source,bash]
----
#!/usr/bin/env bash
set -euo pipefail
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
# shellcheck source=lib/perf-stats.sh
source "$SCRIPT_DIR/lib/perf-stats.sh"

RUNS=${1:-3}
DEVICE=${PIGGY_DEVICE:-emulator-5554}
APP_ID=${PIGGY_APP_ID:-com.lightningpiggy.app.dev}

totals=()
for i in $(seq 1 "$RUNS"); do
  perf_gfxinfo_reset "$DEVICE" "$APP_ID"
  [ "$i" = "1" ] && perf_perfetto_start "$DEVICE" 40000 "$APP_ID"

  t1=$(date +%s%3N)
  # … your scenario here: launchApp, tap, wait, etc …
  t2=$(date +%s%3N)
  totals+=("$((t2 - t1))")
  printf '  run %d: %d ms — ' "$i" "$((t2 - t1))"
  perf_gfxinfo_sample "$DEVICE" "$APP_ID"

  [ "$i" = "1" ] && perf_perfetto_stop "$DEVICE" "/tmp/my-trace-$(date +%H%M%S).pftrace"
done
perf_stats_report "My measurement" "${totals[@]}"
----

`expo-location` reads through Android's AOSP `LocationManager` — no

== Native Nostr pipeline (epic #1036)

Stage 2 moves the hottest Nostr work off the JS thread into
`modules/nostr-native` (rust-nostr's published Kotlin bindings — see the
architecture decision on #1036):

- *M1 (crypto, #1046)*: nip44 encrypt/decrypt + schnorr sign/verify as sync
  JSI functions behind the `src/services/nostrCrypto.ts` facade, flag
  `EXPO_PUBLIC_NATIVE_CRYPTO=1`. Emulator benchmark: ~51× on nip44-decrypt.
- *M2 (relay engine, #1049)*: a rust-nostr relay pool owns the kind-1059
  gift-wrap subscription — sockets, verification and the two-layer NIP-59
  unwrap all run natively; JS receives ≤150 ms-coalesced batches of
  plaintext rumors. Flag `EXPO_PUBLIC_NATIVE_ENGINE=1`, *nsec + Android
  only* (Amber/NIP-46 wraps can only be decrypted by their remote signer;
  iOS is a later milestone). `EXPO_PUBLIC_NATIVE_ENGINE_XCHECK=1` (dev)
  runs both paths and diffs delivered wrap ids. Benchmark:
  `node scripts/bench-engine-relay.mjs` on the host, then a dev build with
  `EXPO_PUBLIC_NATIVE_ENGINE_BENCH=1` — `[PerfBlock] engineBench` lines
  report wall-clock + JS-heartbeat gaps for a 200-wrap backlog drain on
  each path.

Guidance shift once the engine is on: the receive-path JS-thread rules in
this document (yield pacing, decrypt-once gating, coalesced `setState`)
still apply to the JS fallback path — which remains the default and the
only path for Amber/NIP-46 and iOS — but for engine-mode nsec accounts the
per-wrap decrypt cost leaves the JS thread entirely, so reconnect-backlog
freezes show up (if at all) as batch-ingest gaps, not crypto gaps.

== Kind-4 replay verification after restart (v1.5.0)

The Pixel log from 2026-10-13 records a 42,801 ms heartbeat gap during a
44,086 ms `refreshDmInbox`. `fetchInboxDmEvents` alone took 43,495 ms and
returned 449 sent + 921 received kind-4 events, plus 228 gift wraps. The
crypto summary reported `schnorrVerify n=1374 p50=33.94ms p95=35.98ms`.
That count is cumulative for the process, not an exact per-refresh count;
the preceding summary was 110. The receive path and volume implicate
kind-4 relay replay, before the inbox's DB decrypt-once gate. The pool
already uses structure-only checks for kind-1059 and batch kind-0; stored
plaintext inbox loading does not verify signatures. No stack trace was
captured, so unrelated concurrent signed events may contribute to the count.

`nostrVerifyCache` now persists successful signature checks in app-private
AsyncStorage shards: event id (also its canonical hash) plus signature.
Every hit re-hashes the received content and compares the signature; ids
that only passed structure validation never enter this store. Hydration
and shard serialization use budget-gated pacing. RAM holds at most 20,000
records; each of 256 shards holds at most 128. Evicted/corrupt/missing
records fall back to full verification. Existing installs perform one
paced verification pass to populate this new store; old DM rows cannot
safely establish signature trust because they lack the signed envelope.

`nostrRelayReceiveQueue` shares one 4 ms budget across all shared-pool
sockets, dispatching each wire message through the original SDK verifier,
filter, dedup and delivery path. It yields before the next unit when the
budget is spent. Wire EOSE and EOSE timeouts wait behind already received
events; `querySyncAbortable` also queues its independent deadline at that
receive boundary, so pre-deadline events drain even beyond `maxWait`.
Explicit abort still closes immediately. Verification trust is flushed
before EOSE or deadline completion. AUTH, OK
and COUNT replies bypass the backlog. Closing a subscription drops its
queued delivery. The queue is bounded at 20,000 jobs / 8 MiB of estimated
UTF-16 payload; overflow closes the affected relay for a later refetch.

Count-based Jest fixture (native crypto off): 1,300 cold Schnorr checks
before persistence, *zero* after restarting RAM and hydrating trust. A
fake-clock fixture of 1,300 indivisible 34 ms verification units records
at most 34 ms work between timer yields. This is a scheduling/count proof,
not a new Pixel wall-clock measurement. An individual JS crypto call or
large event parse/hash can exceed 50 ms on slower hardware; cooperative
pacing cannot interrupt it. Native crypto remains the eventual solution
for that single-unit cost.

Persistence failure, cache eviction, or process death before a live-event
debounce finishes can require another paced verification. Verification
records contain public ids/signatures, not DM plaintext. They rely on the
same app-private storage trust boundary as local message history. A first
uncached backlog still takes significant total time, but taps can run
between checks. The receive/prepare hooks are public SDK methods guarded
by an integration test; check their binding/EOSE semantics on SDK upgrades.

== Authoring best practices (the rules)

The condensed version lives in `CLAUDE.md` -> "Performance rules" (what every
contributor and agent reads); this section carries the rationale. The
mechanical subset is CI-gated by `scripts/check-perf-antipatterns.sh`
(grandfathered per-file baseline, mirroring `check-file-size.sh` - shrink the
counts, never grow them). The rules map 1:1 onto Stevie's 12-category audit,
so a clean audit and a rule-following codebase are the same thing.

[cols="1,3,2"]
|===
|Rule |Why |Canonical example

|Batch event ingest (never per-event `setState`)
|A relay burst delivers 50+ events synchronously; a `new Map(prev)` clone per
event is O(N) copy + React commit x50, pinning the JS thread for seconds
(#554's wedge mechanism).
|`src/utils/useCoalescedMap.ts` (<=150 ms coalesced flush; leading-edge for
the first event)

|Focus-gated subscriptions, one owner per dataset
|Blurred tabs holding live relay subs waste JS-thread parse work forever;
sibling screens opening duplicate subs double it.
|`useFocusEffect` arming in `useHuntCommunity`; data-via-params fix in #1028

|Staggered resume handlers
|Five independent `AppState 'active'` handlers firing concurrently after a
long Doze is the #554 storm. Latency-insensitive work waits ~3 s (cancellable
timer); only the DM re-arm is immediate.
|`useCacheNotifications` stagger (#1031)

|Deferred cold-start work takes a startup-queue slot
|Independent "wait ~3 s" timers all fired in the same instant, stacking the
Marmot session, NIP-171 session, watcher and push registration, swap recovery
and the BTC Map cache parse onto one frame. The queue runs one task at a time,
at its slot, after JS-thread idle, waiting at most 2 s for each to settle.
`[Perf] startup task <name> fired` shows the real timeline.
|`scheduleStartupTask` + `STARTUP_SLOTS` (`src/services/startupTasks.ts`)

|Bounded relay filters
|An unbounded REQ backfills the relay's whole index through the JS thread on
every mount. Always `limit`, plus `since` where event semantics allow. NIP-59
gift wraps randomise `created_at` up to 48 h back, so kind-1059 must NOT use
`since` (#469) - bound by `limit` and reconcile on re-arm instead.
|30-day window on recent-caches queries (#1029)

|Budget-gated yielding in heavy loops
|An unconditional `yieldToEventLoop()` costs a 16 ms RAF per item - 3x the
cost of the work it paces on single items. The scheduler yields only when the
~4 ms frame budget is spent.
|`createYieldScheduler` (`src/services/nostrDecryptPacing.ts`)

|Memoised rows, expo-image, virtualized lists
|Unmemoised rows re-execute the whole list per trickling profile fetch; bare
RN `Image` re-decodes per mount; `ScrollView` renders everything eagerly.
|`React.memo(LeaderboardRow)` (#1028); `expo-image` +
`cachePolicy="memory-disk"`

|Memoised context values
|One inline `value={{...}}` literal re-renders every consumer on every parent
render - the classic invisible cascade.
|`NostrContext` / `WalletContext` provider values

|Lazy screens
|Eager imports of detail screens put their parse cost (and their native-module
imports) on cold start.
|`lazyScreen(...)` in `AppNavigator.tsx`

|No new crypto on the JS thread
|All Nostr crypto is pure-JS (`nostr-tools` + `@noble/*`) today: 2x NIP-44
decrypts per received wrap, 2x(N+1) sign+encrypt per group send. The ceiling
fix is native (epic #1036: Stage 1 JSI crypto primitives, Stage 2 rust-nostr
engine via the bdk-rn UniFFI pattern - one Rust core, generated Kotlin AND
Swift bindings). Until then, treat every added crypto call in a hot path as a
regression.
|`bdk-rn` as the in-repo precedent

|Prove perf-sensitive changes
|Means hide regressions; a claim without p50/p95 is a vibe.
|`[PerfBlock]` markers (preview builds), `scripts/perf-*.sh` before/after in
the PR body
|===

== Relay subscription capacity (#1399)

`healthAwarePool` budgets REQs independently for each relay/socket on both
shared and Market pools, including raw relay reads for snapshots, contact-list
reconciliation and reactions. The default is 10; NIP-11 discovery may lower it to
`limitation.max_subscriptions`. Discovery is asynchronous, limited to two
HTTP requests, with a 3-second timeout. A configured limit can be supplied
with `pool.setRelaySubscriptionLimit(url, max)`.

Kind-1059 / kind-4 inbox work has first priority, Welcome key-package and
initial kind-445 group-state reads second, and profile / reaction / market /
backfill continuation work third. Only live owners may be preempted.
At the default limit of 10, live owners use at most 7 slots, reserving 3
for one-shots. For smaller limits, live/one-shot reservations are 2/2 at
4, 2/1 at 3, and 2/0 at 2. At limits 1–2 a one-shot temporarily pauses a
live owner, which resumes afterward. Limit CLOSED messages retry with bounded
exponential backoff. Since a NOTICE carries no subscription id, a limit
NOTICE closes and retries all possibly refused REQs, with the inbox first
and a reduced budget. Live owners remain subscribed after EOSE; one-shot
queries release each answered relay immediately and have an overall deadline
that includes connection time and queueing. Abort, account switch and pool
shutdown cancel queued work too. Every one-shot has a budget-owned deadline
of at most 20 seconds, even if its caller abandons the promise. Physical CLOSE
is sent before reusing the slot; a canceled connection or AUTH completion
cannot open a late REQ. Socket close disposes both active and queued owners.
After 15 seconds at capacity, the watchdog logs one `budget stall` warning
with the oldest queued label and holder counts; `budget timeout` names each
one-shot force-released at its deadline. These warnings are always enabled.

Marmot live subscriptions merge compatible group filters into one filter with
all group ids in its `#h` array. This REQ is live-only: `since` is refreshed
at every physical arm to now minus 60 seconds, with a modest limit of 100.
Split a filter only above 256 group ids or the 64 KiB serialized UTF-8 bound
(with 256 bytes reserved for REQ framing and the subscription id); split
filters share one physical REQ when they fit. If the routing set exceeds one
message, rotate REQs every ten seconds on one group slot. Old REQs close
before rebuilding. This keeps 41 groups at limit 4 and 201 groups at limit 10
on one group slot alongside the inbox.

History is separate: subscribe, budget resume and socket reconnect trigger
independent per-group catch-up from each group's cursor with the existing
10-minute slack. Bounded one-shot pages share the relay budget and yield
between pages and delivery batches. Short pages are not assumed exhausted:
relays can clamp the requested limit. All pages are collected and sorted
before delivery, and live events wait behind recovery so they cannot advance
a group's cursor past a missed commit. A pass that hits the 40-page cap with
older events unread continues below its oldest event next pass. Memory is
bounded at 20,000 events per group by keeping the oldest and dropping the
newest, which are re-read from the advanced cursor once the older range is
delivered, so a longer history still arrives oldest-first, in passes. A
duplicate-only page as full as any the relay served marks a second holding
more events than one page: paging steps past it and warns rather than
reporting exhaustion after one page. A recovery read is authoritative once
any relay reaches EOSE; it fails (cursor and buffer retained, retried with
backoff) only when no relay does, so one dead, AUTH-gated or slow relay in a
group's list cannot hold its live delivery. The live buffer holds at most
1,000 distinct ids and on overflow is dropped and re-read from the retained
cursor. A group relay whose socket keeps failing re-arms with exponential
backoff (one second doubling to a minute, reset by a successful arm). Event dispatch checks each owner's
original filter and rejects ambiguous `h`
tags before the Marmot engine's signature and group checks. Profile rounds
combine the former three 50-author REQs into one 150-author filter and close
at EOSE. The provider arms its sole inbox at login, before first Messages
focus. Gift wraps retain `limit` without `since`. Welcome joins reuse the
already decrypted rumor and local MLS key material. Multi-filter Marmot
lookups (including Welcome ownership verification) send one fresh REQ per
relay, rather than one REQ per filter.

Fake-pool evidence (`healthAwarePoolBudget.test.ts`): 20 groups sharing
Primal and Snort plus seven legacy/cache/DM owners require 27 REQs per relay
before merging and 7 after (one live owner waits). Saturation holds the default peak at 10 and
preempts background work for the inbox. CLOSED/NOTICE regressions fail
against the original pool. These counts describe the test fixture, not a
measured device peak or Primal's actual enforced limit.

Group backfill already pages backwards in 500-event pages (up to 40 pages).
The 1,200-event regression drains three bounded pages, then receives a live
event; there is no 512-event page cap in this path. A busy group's ingestion
can delay that group's live attachment, but cannot consume the inbox's slot.

----
rg '\[Relay\] budget|\[Marmot\] inbox armed on|\[Marmot\] group subs merged:' app.log
----

Expected lines include `[Relay] budget <relay> open=N/max queued=M`,
`[Marmot] inbox armed on <relay>`, and
`[Marmot] group subs merged: N groups -> M REQs on <relay>`.
A stall reports `[Relay] budget stall <relay> open=N/max queued=M
oldest=<label> <age>s holders: <label>×N ...`; deadline recovery reports
`[Relay] budget timeout <relay> label=<label>`. A successful Welcome then
reports `[Marmot] joined <group> from welcome` in development builds.
