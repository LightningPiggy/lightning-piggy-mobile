= Data storage architecture

How Lightning Piggy persists data on the device: what lives where, what's
sensitive, and what's encrypted. Read this before adding a new cache or
changing how anything is stored.

== Principles

* *Secrets go in the OS keystore.* Anything that is itself a credential —
  the Nostr `nsec`, an LNURL-withdraw bearer, an NFC tag lock PIN — lives
  in `expo-secure-store` (Android Keystore / iOS Keychain, hardware-backed).
  Never in AsyncStorage or a plain file.
* *Bulk data goes in AsyncStorage or files,* not the keystore — the keystore
  is for small secrets (a key, a token), not megabytes of cache.
* *Public vs private.* Nostr public events (geo-caches, NIP-52 events, BTC
  Map places) are public data — they need no at-rest encryption. *Decrypted
  DM content is private* — it does, and is the subject of the encrypted-store
  work (see <<target>>).
* *The decrypting key is the protected thing.* As long as the key is in the
  keystore, ciphertext on disk is useless without it. Peer clients stop here
  and leave the at-rest data unprotected: Damus keeps the `nsec` in the Keychain
  but stores event data unencrypted; Amethyst holds decrypted data in memory
  only; 0xchat's Isar DB is plaintext on disk. We go one step further and
  encrypt the at-rest DB too (Signal's model) — see <<target>>.

[[marmot-kv]]
=== Marmot (MLS) state: `marmot_kv` namespaces

One row per `(owner, namespace, key)`; values are JSON with `Uint8Array` /
`bigint` tagged (`marmotStore.ts`). `owner` is the account pubkey, so accounts
on one device never share MLS state, and a per-account sign-out deletes every
row for that owner (`deleteMarmotStateForOwner`, from `wipeDmStoresForAccount`).

[cols="1,3",options="header"]
|===
| Namespace | Contents

| `groups` | MLS group state per group (ratchet tree, epoch secrets, retained epochs) — owned by `marmot-ts`.
| `keyPackages` | Our key packages' private keys and the events they were published as.
| `invites`, `lifecycle`, `ingest`, `rewind`, `removed` | Other `marmot-ts` client stores: received invites, group lifecycle records, ingest / convergence evidence, the per-group fork-history tree used for fork recovery, and "removed from this group" markers.
| `history:<group id>` | Durable decrypted app events (rumors, ours included) per group. Replayed for the last 7 days on start so a message the app died before storing is recovered; pruned to the newest 500 per group. Reactions in Marmot 1:1 threads are read back from here.
| `mediaKeys:<group id>` | Per photo message: the vetted Blossom URL and candidate file keys (MIP-04), derived on arrival or on send. Pruned with its `history:` entry.
| `pushRecords` | Per group: verified MIP-05 push records (encrypted device tokens, server pubkey, relay hint, owner proof) and removal tombstones, keyed by (member, leaf, platform, server).
| `pushShareTs` | Per group: the highest MIP-05 `owner_ts` we have signed (447 or 449), kept after a removal so our next entry always outranks our own tombstone.
| `pushShare` | Per group: the signed MIP-05 record *we* last published for this device (our token sealed to our notification server — never the raw token) and the group's leaves at the time, so a restart re-signs nothing and a new member gets the same record re-sent. The opt-in itself is a per-account setting in AsyncStorage (`marmot_push_enabled_v1_<pubkey>`, removed with the account — if that delete fails, the account goes on a SecureStore tombstone list, `marmot_push_forgotten_v1`, honoured and retried at every start so a re-login never revives the opt-in; the device-wide `marmot_push_server_v1` holds a custom server); the raw FCM/APNs token is never stored — it is re-read from the OS at each start. The notification-watcher opt-in (DMs, zaps, mentions, payments) is per account in AsyncStorage (`watcher_push_v1_<pubkey>`): the chosen categories, the last registration `ts` (kept strictly increasing), and a record of what was last registered — fingerprints, app id, platform, when, and a *hash* of the token, never the token. Wiped on sign-out.
| `pendingWelcomes` | Welcomes whose join failed transiently, retried at the next session start.
| `welcomes` | Welcome rumor ids already joined or permanently rejected (each Welcome is joined at most once).
| `firstSeen` | When this device first saw each group (ms) — MLS carries no creation time; it orders DMs (newest wins) and groups.
| `watermark` | Per group: `created_at` of the newest *ingested* kind-445, the `since` for the bounded backfill.
| `meta` | `keyPackageSlot` — the random 32-byte `d` slot reused for every key package this account publishes from this device.
| `deviceKeys` | Per MLS leaf signature key: the app that published the invitation key (key package) it came from (`client` tag) and when — recorded when we invite a device, or found by the members sheet's bounded relay lookup. Drives the per-device app names (#1267).
| `deviceLeaves` | Per group: the leaves (devices) as of the last commit this device processed, with the epoch and time each was first seen and when a person last lost a device. Read-only bookkeeping over group state for the devices UI.
| `deviceNotices` | Per group: the alpha-only "X joined on 2 devices" lines drawn locally from commits (newest 50). Never sent; shown only with the developer switch on.
|===

`dm_messages.protocol` is `'marmot'` on Marmot 1:1 rows and NULL otherwise.
Marmot text is stored as kind 14 and photos as kind 15 (the `#lpe=1` URL with
`alg=encrypted-media-v2`), so the column, not the kind, identifies the
transport. Marmot rows of non-message kinds (reactions, deletions, push-token
gossip, …) are never written, and rows earlier dev builds stored are purged
on start (`deleteMarmotRowsOfKinds`).

[[threat]]
== Threat model: device seizure

The at-rest design assumes the strongest realistic adversary for a travelling
user: *the phone is seized (e.g. border control) and forensically imaged*,
possibly while powered on and after first unlock.

* *What the design protects:* every 1:1 DM ever decrypted — content, delivery
  metadata, optimistic sends — exists on disk only inside `lightningpiggy.db`,
  which is SQLCipher ciphertext end-to-end (content *and* metadata). The
  256-bit DB key never touches disk outside the hardware keystore
  (`expo-secure-store`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` — excluded from
  backups, not device-migratable). Imaging the flash yields ciphertext; the
  key material is wrapped by the secure element and is not extractable
  without defeating the hardware (or coercing the device unlock itself — no
  app-level design survives a compelled unlock; see the app-lock follow-up).
* *Wallet + identity secrets* (`nsec`, NWC URLs, mnemonics, xpubs, LNURL-w
  bearers, the DB key) are individually keystore-wrapped — same story.
* *Known residual plaintext (accepted, tracked):* decrypted *group-chat* logs
  (`group_history_<ownerPubkey>:<groupId>`, `nostr_group_activity_<pubkey>`)
  still live in AsyncStorage — each account's logs are wiped on that account's
  sign-out (#944, #1240) but readable from a seized unlocked device until they
  get the same encrypted-store treatment (follow-up). This includes *Marmot*
  group logs (`group_history_<ownerPubkey>:marmot:<mls group id>`),
  whose photo rows embed the photo's file keys in the `#lpe=1` URL. Marmot
  1:1 rows and all MLS state are in the encrypted DB.
* *Group-chat logs are per account (#1240).* Before #1240 they were
  device-wide (`group_messages_<groupId>`) and any sign-out deleted every
  account's logs. On upgrade, `groupMessagesMigration.ts` *copies* each legacy
  blob to every local account that is a member of the group (its
  `nostr_groups_<pk>` lists it — for a synthetic NIP-17 room only if the id
  re-derives from that entry's members plus the account — or its `marmot_kv`
  state holds it), and only then deletes the legacy key. A shared legacy log
  therefore lands in *every* member account; per-account separation applies
  to history from then on. A blob no account owns is never shown and is
  deleted at the next sign-out (`releaseLegacyGroupLogs`, which first
  re-attributes it); one whose Marmot lookup failed is kept only while
  another account remains. The first pass also deletes every
  `nostr_group_activity_*` rollup once (flag
  `group_activity_rollups_reset_v1`; pre-#1214 builds leaked previews into
  them, and they rebuild from each account's own history). Copies are merged
  uncapped, so the migration never drops a message. Writes for an account
  that has just been signed out are refused until it is active again. The per-account prefix (`group_history_`) is deliberately
  disjoint from the legacy one: group ids come off relays, so a crafted id
  like `<pubkey>:g_room` must never be readable as that account's history.
  Group history and rollup reads await the migration and never fall back to
  a legacy key.
  Public caches (places, profiles, geo-caches) are public data by
  definition; the eventual move into the one encrypted DB is a metadata-
  privacy nicety, not a confidentiality requirement.
* *Out of scope at the app layer:* a compelled/observed device unlock, a
  rooted device with the app running (RAM holds decrypted rows while the UI
  displays them), and platform supply-chain compromise. Mitigations that
  raise the bar further — an app-level lock gating the DB key read, a panic
  wipe — are candidate follow-ups, not current features.

== Gotcha: the 2 MB AsyncStorage row limit

AsyncStorage stores each key as one row in Android's SQLite. Android's
*CursorWindow caps a single row at ~2 MB on READ* — a value past that throws
`SQLiteBlobTooBigException` and the row fails to hydrate. A large cache stored
as one JSON blob therefore *silently fails to load*, which is what caused the
DM cold-start re-decrypt freeze (#687): the wrap cache blew the limit, hydrated
empty, and the app re-decrypted the whole inbox on every launch (64-88 s).

Interim fix (#689): the NIP-17 wrap cache moved to a *file* (`expo-file-system`),
which has no per-row read cap. *Do not store an unbounded cache as a single
AsyncStorage row.*

The file move fixed the cold-start *seed* but not the underlying cost: a
focus-triggered `refreshDmInbox` still walks the whole inbox synchronously on
the JS thread. Measured on a real device (2026-05-26), opening the Messages tab
ran `refreshDmInbox` for *52 s* and froze the JS thread for *49 s in one
unbroken block* — while opening an individual conversation was ~2 s (cache hit).
A single conversation reads fast; the inbox-wide pass does not. That asymmetry
is the case for <<target>>.

[[target]]
== Target architecture (#695): indexed, encrypted SQLite

NOTE: *Status:* the DM slice of this architecture is *complete* as of #850 —
`dm_messages` is wired into the inbox refresh, the live DM subscription and
thread opens (ingest via `dmWrapIngest`/`dmIngest`, reads via `dmDb`'s indexed
queries), and is the *sole* at-rest home for 1:1 DM content: the plaintext
wrap-cache file was retired in #848 (`dmStoreMigrationRunner`) and the
plaintext inbox/conversation AsyncStorage blobs in #850 (`dmBlobMigration`),
each via a one-time verified populate → delete → verify migration.
Transactions/swaps and the public cache tables remain future slices; group
chat is the known plaintext residual (see <<threat>>).

The blob/file caches don't scale (whole-blob parse, no indexes, the 2 MB trap).
The target — matching how 0xchat / Damus persist Nostr data — is a single
*indexed local database*:

* *Engine:* `op-sqlite` (bundles SQLCipher). Chosen over `expo-sqlite` because
  SQLCipher gives *transparent whole-file encryption* (content *and* metadata),
  so turning encryption on is just opening with a key — no schema/query change.
* *One row per event,* not a blob. Indexed by `event_id` (unique → O(log n)
  dedupe), `created_at`, and `conversation`/`geohash`/`author` as needed →
  fast paginated reads, no whole-blob parse, no 2 MB ceiling.
* *Decrypt once at receipt → store plaintext rows.* Cold start becomes an
  indexed read with no re-decryption (the 0xchat model).
* *At-rest encryption from day one* (see <<keys>>) — so decrypted DM plaintext
  is never written to disk in the clear (closes #690). This is the gap every
  peer client leaves open; we close it (Signal's model).
* *Sync:* persistent `kind:1059` subscription + a `since` cursor rewound ~3
  days (to absorb NIP-17's randomised gift-wrap timestamps), advanced off the
  *inner* rumor's real `created_at`, deduped by id — so we stop re-querying the
  whole wrap set on every open.

=== What goes in the DB

[cols="2,2,2",options="header"]
|===
| Data | Row keyed by | Encrypted?
| DM wraps / messages (NIP-17) | `event_id` (+ `conversation`, `created_at`) | *Yes* — private content
| Transactions (Lightning / on-chain) | `payment_hash` / txid (+ `wallet_id`, `created_at`) | *Yes* — private financial
| Boltz swaps | swap id (+ `status`, `timeout_block`) | *Yes* — private + recovery-critical
| Geo-caches (NIP-GC 37516) | `coord` (+ `geohash`, `author`) | Harmless (public); encrypted anyway since one DB
| NIP-52 events (31923) | `coord` (+ `geohash`, `starts_at`) | Harmless (public)
|===

DMs, transactions, and swaps are *private* and the reason the DB is encrypted.
Geo-caches and events are *public* but folding them into the same SQLCipher DB
is simpler than a second plain DB, and the overhead is negligible.

*BTC Map places are the deliberate exception* — public *external bulk* data,
identical for every user and refreshed wholesale, so they stay in their own
*plain* cache (`btcmap-last-result.json`), **not** the encrypted DB. That keeps
the encrypted DB strictly *your* data, so logout = a clean, complete wipe (see
the storage map under <<Diagrams>>).

*Sequencing:* DMs first (they cause the freeze and need encryption);
transactions/swaps next (financial); the public Nostr tables after.

[[keys]]
== Keystore key management (for the encrypted DB)

Signal's wrapped-key model. The key module (`src/services/localDbKey.ts` —
`getOrCreateLocalDbKey` / `clearLocalDbKey`) is the first slice of the #695/#690
work, added in #697. One key opens one DB
holding *both* the private DM rows and the public cache rows — the name is
deliberately not DM-specific:

. *First run:* generate a random 256-bit DB key.
. *Store it in `expo-secure-store`* (Keystore/Keychain, hardware-backed where
  the device supports it) with `keychainAccessible: AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`
  so it is never iCloud/device-migration backed up — a 32-byte key is well
  within the keystore's remit (unlike the bulk cache).
. *App start:* read the key from secure-store → open the SQLCipher DB with it
  (`PRAGMA key`). The on-disk file is ciphertext; the key only lives in RAM at
  runtime.
. *Optional:* auth-gate retrieval (device unlock / biometric).
. *Logout / account wipe:* delete the DB file *and* the key from secure-store.
  *Rotation:* new key + `PRAGMA rekey`.

The hardware keystore wraps the key, so raw extraction of the DB file *or* the
key off the device yields nothing usable.

=== Buyer order lifecycle admission and history

Live and backfill NIP-17 ingest accept incoming payment requests, status,
shipping updates and receipts only when the order id matches this account's
stored outgoing type-1 order and the sender is that order's seller. Rejected
lifecycle events increment a bounded per-account diagnostic counter and never
enter the encrypted DM store. Incoming type-1 orders remain available to the
seller flow. Messages' Only friends setting controls inbox entries and alerts;
a matching invoice still refreshes an open conversation after persistence.

`getOrderRows` selects the newest 500 placed orders (configurable up to 2,000),
then retrieves all lifecycle rows for those order ids and seller conversations.
The limit counts purchases, so hundreds of newer status updates cannot evict a
placed order or its invoice from My orders (#1563). Invalid legacy JSON and
updates from unrelated sellers are excluded.

=== Migration (old store → new): import the decrypt memo, then delete

Relays remain the *canonical source* for messages. But the old plaintext
caches were never independent data — they were purely *memos of decryptions*
this app already performed on relay-fetched events. So the one-time
migrations import each memo as rows, then delete the plaintext with
verification (ordering enforced by `dmStoreMigration`: populate → delete →
verify → flag; a crash anywhere retries next launch, and plaintext is never
deleted before the DB holds the rows):

* *#848 (`dmStoreMigrationRunner`)* — the file-backed NIP-17 wrap cache
  (closing the original at-rest gap, #690).
* *#850 (`dmBlobMigration`)* — the last two plaintext blobs: the inbox
  summaries (`nostr_dm_inbox_v1_*`) and the per-conversation threads
  (`nostr_dm_conv_v1_*`). The conversation import is the only carrier of the
  delivery ticks (#856), rumor ids (#857) and optimistic `local-` rows, so
  the import is *fill-only*: an existing encrypted row always wins; the blob
  only supplies rows the store lacks plus missing tick/rumor columns. The
  delete step also removes any pre-#288 *unsuffixed* wrap-cache remnants
  (delete-only: an unowned cache can't be attributed on a multi-account
  device, and its content is re-fetchable).

Why import rather than the originally-planned "re-fetch and re-decrypt"?
Re-decrypting the whole inbox on migration day is exactly the cold-start
decrypt sweep #846/#847 eliminated (~25 ms × hundreds of wraps on the JS
thread). The memo preserves decrypt-once across the migration at the cost of
one file read + one DB transaction. Anything the memo didn't cover is
re-fetched from relays and decrypted once by the normal ingest path — so the
worst case (corrupt/missing cache) degrades to the re-fetch plan, never to
data loss.
