# Ark (bark) in Lightning Piggy: integration plan

Status: draft, for discussion with the maintainers. Everything below sits behind a
build-time flag and runs on **signet only**.

Ark is a Bitcoin layer 2. Users hold off-chain coins (VTXOs) that a server co-signs,
pay each other instantly and almost for free, pay and receive Lightning through the
server, and can always leave on-chain, cooperatively or, if the server disappears,
on their own (an "emergency exit"). [bark](https://second.tech/docs) is Second's
implementation; `@secondts/bark-react-native` is its React Native binding (UniFFI,
New Architecture + Hermes, both already used here).

## Why Ark fits Lightning Piggy

- **Small balances stay self-custodial without channels.** Pocket money and
  allowances are tens to thousands of sats. A Lightning channel per family member is
  too expensive to open and to keep liquid for that, and NWC to a custodial wallet
  means trusting the wallet provider. An Ark coin needs no channel and no inbound
  liquidity, and the holder can always take it out on-chain.
- **Instant, near-free payments inside the family.** Parent to saver, and saver to
  saver, is an Ark-to-Ark payment: no routing, no channel balance, fee close to zero.
- **Still a Lightning wallet.** The same wallet pays BOLT11 invoices, Lightning
  addresses and LNURL, and receives over Lightning, so it fits the app's existing
  payment surface.
- **One recovery phrase.** No channel backups, no watchtower.

The honest trade-off: Ark coins expire (about 28 days for coins from boards and
refreshes, 1 to 3 days for coins from a Lightning receive, per
[VTXO lifetime](https://second.tech/docs/learn/lifetime.md)) and must be refreshed
before then, and an emergency exit of a very small coin can cost more in on-chain fees
than it is worth. Both are central to the plan below.

## What this branch does (Phase 1)

Flag: `EXPO_PUBLIC_ENABLE_ARK=1` at build time. Without it nothing changes: no
settings row, no screen registered, no native libraries linked
(`react-native.config.js`), no Expo plugin (`app.config.ts`), and the JS never
`require`s the module.

### Key choice: a separate recovery phrase

The Ark wallet gets its own BIP-39 phrase (generated by bark or restored by the user),
stored in SecureStore with the same `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` option as
the on-chain mnemonics. It does **not** derive from an existing seed because:

- most on-chain wallets in the app are watch-only (xpub), so there is often no seed;
- the hot-wallet mnemonics hold mainnet funds and this runs on signet, so test
  software should never handle a real-money seed;
- two wallets driving one seed race on key indices and server-side state;
- the Nostr key is a messaging identity, may live in Amber / NIP-46, and must stay
  rotatable, so it should not double as a money key.

If you would rather have one phrase for everything, bark accepts any BIP-39 phrase and
derives its own paths, so a shared seed is possible later. It needs a decision on
backup UX first (see open questions).

## Phases

### Phase 1: Ark wallet behind a flag (this branch)

Done as above. Remaining before it could leave draft:

- Native build and a manual run on Android and iOS (not possible on the machine this
  was written on; see "Testing").
- Before/after screenshots for the PR.
- A Maestro flow (`.maestro/wallets/`): create wallet, fund from the signet faucet,
  send to a second test identity.

### Phase 2: Ark as a wallet card

- Add `walletType: 'ark'` next to `'nwc'` and `'onchain'` in `src/types/wallet.ts`, so
  Ark appears on the Wallets carousel and in the existing Send / Receive sheets
  instead of a separate settings screen.
- Do it by extracting an Ark adapter hook rather than growing `WalletContext.tsx`,
  which is already over the 1,000-line cap.
- Map bark notifications (`WalletNotifications`: movement created / updated) to the
  app's incoming-payment announcer, batched like other live events.
- Decide scoping: one Ark wallet per device (today) or per Nostr account (the app's
  `perAccountStorage` pattern). Families share devices, so probably per account.

### Phase 3: Allowances as small Ark coins

- A parent sets a recurring allowance (amount + schedule) for a saver's Ark address.
  The parent's app pays it as an Ark-to-Ark payment, which is near-free.
- The saver's phone does not need to be online to be paid by Ark. To be paid over
  Lightning while offline, bark can create an invoice whose claim goes straight to
  another Ark address (`bolt11InvoiceForAddress`): the parent's always-on phone can
  receive a zap on the saver's behalf without custody (it cannot redirect the
  payment, but must stay online to deliver it).
- Show allowances in the saver's history with the parent's Nostr profile (the
  existing zap counterparty UI).
- Keep allowance coins few and not too small: consolidate on refresh, so exits stay
  economical.

### Phase 4: Refresh and expiry, also while the app is closed

This is the main operational risk for a family app whose phones may sit unopened for
weeks.

- Today: the bark daemon runs while the app is open (sync, Lightning claims and
  bark's background maintenance; to confirm on device that it refreshes coins near
  expiry on its own), the screen warns early (`refreshSoon` at ~4 days, `urgent`
  under one day) and offers a manual refresh.
- Next: run `maintenanceDelegated()` / `refreshVtxosDelegated()` from the existing
  `expo-background-task` worker. Delegated refresh is designed for sleeping mobile
  wallets: the user signs ahead and the server completes the refresh in a later
  round.
- Next: a local notification ("Open Lightning Piggy to keep your sats fresh") a few
  days before the first expiry, using the existing notification service.
- Coins from a Lightning receive live only 1 to 3 days, so the app should refresh
  them soon after the claim.
- After expiry the server can sweep the round. Refresh, Lightning send and offboard
  still work with the server's cooperation; Ark sends and emergency exits do not.
  The UI copy must say so plainly.

### Phase 5: Exits

- Cooperative "move everything on-chain" (offboard) and on-chain sends are in Phase 1.
- Emergency exit is in Phase 1 as a guarded, destructive action with a progress call
  on every screen visit. Still to do: persistent progress UI (exit state per coin,
  `getExitStatus`), CPFP fee funding guidance (bark's on-chain wallet pays), and a
  claim flow that prefills the user's own on-chain wallet address.
- Warn when an exit would cost more than the coins are worth (`estimateEmergencyExitFee`).
- Parent-held recovery: a parent may want to be able to rescue a saver's funds. To
  discuss: shared backup of the saver's Ark phrase in the parent's app vs. something
  stronger later.

### Phase 6: Lightning via bark, and mainnet

- Lightning receive and pay are in Phase 1. Next: a Lightning address for the Ark
  wallet (an LNURL-pay endpoint that calls `bolt11Invoice`), so zaps to a saver's
  Nostr profile land in Ark.
- Expose the Ark wallet as an NWC wallet service inside the app, so every existing NWC
  code path (zaps, Boltz swaps, Hunt payouts) works with Ark unchanged. To evaluate
  against simply adding `'ark'` branches.
- Mainnet only after the above, behind a separate flag and an explicit user
  confirmation, against Second's mainnet server (`https://ark.second.tech`).

## Risks

| Risk | Mitigation |
|---|---|
| Coins expire while the app is closed | Daemon refresh while open, early warnings, manual refresh; delegated refresh from background tasks and reminder notifications (Phase 4). |
| Server dependency | Ark sends need the server online. Unilateral exit always works before expiry; cooperative offboard is cheaper. Server choice should be explicit in the UI. |
| Exits are uneconomical for tiny coins | Consolidate coins on refresh, warn before exit when fees exceed value, keep allowance coins few. |
| Native binary size | Native libraries are only linked when the flag is set (`react-native.config.js`). Size impact of a flagged build is not measured yet. |
| `npm ci` downloads bark's prebuilt binaries | The package's postinstall fetches checksum-verified artifacts from GitLab on every install. `SKIP_BARK_POSTINSTALL=1` skips it for CI jobs that do not build natively (lint, tests). This branch was installed with `--ignore-scripts`. |
| Pre-1.0 API churn | Pinned to `^0.25.0` (same as satsigner). The Jest mock documents the surface we use; a bump means rerunning the suite and a smoke test. |
| Wallet data loss | The phrase restores coins via the server mailbox recovery scan, but bark recommends backing up the data directory too. Device-transfer and backup of `documentDirectory/ark/` is not handled yet. |
| Recovery phrase UX for younger savers | Same gate as Back up your key today; a parent-assisted backup is an open question. |
| 0.25.0 known issue | After a JS reload with a bark logger installed, logging can hang `Wallet.open()`. This branch installs no logger. |

## Open questions for the maintainers

1. Is a separate Ark recovery phrase acceptable, or do you want one family seed for
   on-chain and Ark? Who backs up a saver's phrase: the saver, the parent, or both?
2. Per device or per Nostr account?
3. Where should Ark live in the UI: as a wallet card (Phase 2) from the start, or
   behind Advanced until it has run on signet for a while?
4. Would you accept the native dependency in the default build once it graduates from
   the flag, or keep it in a dedicated build variant?
5. Is background refresh via `expo-background-task` acceptable on battery and privacy
   grounds (it talks to the Ark server, not to relays)?
6. Allowances: should they live in the app (parent's phone pays on a schedule) or
   ride on an existing Nostr flow (for example a recurring zap)?
7. Which Ark server(s) to offer? Second runs public signet and mainnet servers; the
   protocol allows others, and the config already takes any URL.

## Testing

Automated (runs in CI as is):

```sh
npx tsc --noEmit
npm run lint
npm run format:check
npx jest src/services/ark src/utils/ark   # 59 tests, native module mocked
npm run i18n:sync -- --check
```

Manual on signet (needs a development build):

```sh
EXPO_PUBLIC_ENABLE_ARK=1 npm run android:dev    # or ios:dev
EXPO_PUBLIC_ENABLE_ARK=1 npm start
```

1. Settings → Advanced → Ark wallet (signet) → Create Ark wallet.
2. Receive → Ark address → copy it into the faucet at https://signet.2nd.dev
   (GitHub sign-in); the balance updates within the 30 s poll.
3. Send to a second test device's Ark address; then pay a signet Lightning invoice.
4. Receive → Lightning → create an invoice and pay it from another signet wallet.
5. Coins → Refresh coins now; then Move everything on-chain to a signet address.
6. Backup → Show recovery phrase; remove the wallet; restore from the phrase.

Not yet verified: a native build (`expo run:android` / `ios`) of this branch. The
Android JS bundle builds with the flag on (`npx expo export --platform android`), and
the autolinking output includes bark only with the flag set
(`npx expo-modules-autolinking react-native-config -p android --json`).
